## Image and destination decisions

Reuse the existing Owner-authorized upload/finalization and immutable sanitized
WebP asset infrastructure from 12.11. The historical `profile_media_*` names and
private `working/profile/` object namespace are storage implementation details.
A new Product image upload does not attach to or replace Identity Working media.
The new preparation references only a finalized same-Owner canonical asset with
validated content type, bytes and dimensions; no raw URL, staging object or
browser-declared image metadata is accepted. Replacing/removing this selection
does not delete the old asset or change Product identity/reference. Future media
garbage collection must include Product preparation references.

Destinations are an ordered bounded array (zero to ten) of structured
`provider_key` and `destination_url` records. One destination suffices; additional
destinations remain optional. Recognition covers Shopee (`shopee.co.id`,
`shope.ee`), Tokopedia (`tokopedia.com`, `tokopedia.link`) and TikTok
(`tiktok.com`), including genuine subdomains, never lookalike suffixes.
Unknown hosts use `external:<normalized-host>` with neutral hostname context,
not an Owner-invented official provider label. Recognition identifies host
context only, not live merchant validity or a safe verdict. One destination per
provider key and no duplicate URL are accepted. Array order is authoritative and
deterministic; no ordering claims cheapest/best. The shared external-destination
policy normalizes URLs without removing creator query/affiliate attribution.
The database independently validates syntax/host/provider binding and rejects
credentials, fragments, IP/local targets and nonstandard ports. DNS/reputation
checks remain the scanner's job, not SQL or provider recognition.

## Persistence and trust boundaries

`core.product_preparations` is private with RLS and no Data API table privileges,
including service-role access. Its existing Product UUID/Owner binding and
same-Owner media foreign key preserve ownership. Reads create nothing. An explicit
save may retain incomplete image/destination preparation for a meaningful existing
Draft; an empty editor never allocates a Product/reference.

Authenticated current-Owner resolver/save RPCs accept no Owner or Product selector.
Save locks Owner, progress and Product, checks the current active/incomplete S5+
prerequisites, expected Product revision and independent preparation revision,
then validates and replaces the complete preparation atomically. Reject stale,
invalid, exhausted or denied mutations without altering prior saved preparation.
Changing Product text/source or persona retains preparation; a stale editor must
reload the current Product revision before saving. Preparation saves alter no
Product/Identity/layout/progress revision, completion, safety verdict or public
state. The web action verifies the exact acknowledgment before scanning only the
acknowledged URLs after commit. Scanner failure keeps saved preparation private
and non-trusted. Resolver/action DTOs expose no Owner UUID or private object key.

The S5 UI supports manual image upload/selection and newline-separated destination
entry without extraction dependency. Failed saves retain inputs and last saved
media. Success is labeled saved privately, never publish-ready or live.
