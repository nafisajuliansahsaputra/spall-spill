# 12.13 — Spill Item identity and reference foundation

## Reconciliation decision

A successful meaningful Product Draft save is durable Item creation, not an
unreferenced staging exception. Preserve its UUID, Owner, source/title, revision,
timestamps, and safety bindings. Allocate the persistent numeric Spill Reference
in that same transaction, independently of publication. URL-only Draft creation
continues to be valid; a recognizable title is required at a later Publish gate.

Existing Drafts receive an identity reservation in an additive migration ordered
by Owner, creation time, and UUID. No existing public reference exists to replace.
The migration takes the Owner-table EXCLUSIVE lock before the content-table lock,
matching live mutation lock order and blocking new-Owner races during backfill.
Ordinary resolver reads remain available. Deploy it in a planned migration window;
its brief write locks cover Owner creation and mutations.
Old migrations remain historical evidence; their no-reference comments are
superseded by this contract and its additive migration.

## Data / transaction boundary

- Private `core.spill_item_identity_registry`: immutable Item UUID, canonical
  Owner UUID, explicit Product/Resource type, positive numeric reference,
  reservation timestamp; unique `(owner_id, spill_reference)`.
- Private `core.spill_reference_counters`: next unused number per Owner, shared
  by both Item types, starts at 1. The numeric range is bounded to JavaScript-safe
  positive integers; exhaustion fails the entire creation transaction.
- Counter UPSERT locks/serializes allocation for the same Owner; different Owners
  may receive the same reference. Rollback publishes/acknowledges no identity.
- Internal allocation also locks and verifies the existing canonical Owner before
  counter mutation. It is not an API and cannot be called by Data API roles.
- A Product insert reserves its identity through a database trigger after content
  validation. Content, counter, and registry changes commit or roll back together.
- Product identity/Owner cannot change on update; title/source/revision edits
  retain their reservation. Stale/rejected saves allocate nothing.
- Registry rows cannot be changed, deleted, or truncated. Counters cannot be
  rewound, moved to another Owner, deleted, or truncated. Item content deletion
  leaves the reservation intact, and recreating a removed UUID is rejected.
- Reservations deliberately have no cascading content/Owner foreign key. They
  contain UUIDs rather than personal content, survive content/Owner deletion,
  and prevent reference reuse. Future destructive/privacy workflows must define
  their own policy without freeing references.

## Security / application boundary

Enable RLS with no client policies, revoke all table/function privileges from
PUBLIC/anon/authenticated/service_role, and keep tables/internal functions in
unexposed `core`. Helpers are SECURITY INVOKER with empty search_path, called
inside the existing authenticated Owner-scoped SECURITY DEFINER save boundary.
No client-supplied Owner/ref allocator or public registry endpoint is added.

Existing resolver/save payloads remain compatible. Registry allocation does not
imply safety approval, public availability, Published state, Spill Activation, or
onboarding completion. Identity connections never receive Spill references.

## Required verification

Test current-Owner save creation, no allocation on reads/invalid/stale/denied
requests, same numbers in different Owner namespaces, shared Product/Resource
allocator numbering, immutable identity/type/reference, retained tombstones,
failure rollback, counter rewind denial, and direct client denial. Rebuild/lint
and run all pgTAP tests in an isolated local database and CI. Separately exercise
concurrent transactions and backfill of a pre-migration Draft. Preserve the
existing local database. S5/S6 closure and live provider gates remain open.
