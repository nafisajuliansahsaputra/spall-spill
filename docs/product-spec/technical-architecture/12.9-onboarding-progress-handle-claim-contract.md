# 12.9 — Onboarding Progress & Handle Claim Contract

## Status

**LOCKED / CURRENT O01 ONBOARDING-FOUNDATION IMPLEMENTATION AUTHORITY**

This contract resolves the implementation details required to begin Stage 6 Onboarding without changing the locked O01 product semantics.

It governs:

- account-side O01 progress persistence;
- O01-S1 Claim Handle;
- O01-S2 Primary Use Case;
- optimistic-concurrency boundaries for onboarding progress;
- current Handle namespace ownership required by S1.

It does not yet define the complete S3-S6 Identity, Starter, first Product/Resource, Preview, or first-publication persistence model.

Those surfaces remain governed by the locked product specification and will receive their own just-in-time implementation contracts before their canonical data models are introduced.

---

## 1. Governing Product Semantics

O01 remains one logical recoverable flow at:

`/onboarding`

Canonical semantic steps remain:

1. `claim_handle`
2. `primary_use_case`
3. `basic_identity`
4. `starter_composition`
5. `relevant_first_job`
6. `preview_publish`

The implementation may represent step state internally, but it must not create six unrelated product destinations.

Primary Use Case changes guidance only. It never changes Owner permissions or capability availability.

No S1/S2 action completes onboarding.

`core.owners.onboarding_completed_at` remains unchanged until the later authoritative first-publish contract is satisfied.

---

## 2. Account-Side Onboarding Progress

Canonical onboarding progress lives in private application-owned PostgreSQL state.

One progress record exists per canonical Owner.

Conceptual relation:

`core.owner_onboarding_progress`

Minimum authoritative fields:

- `owner_id`
- `current_step`
- `primary_use_case`
- `revision`
- `created_at`
- `updated_at`

`owner_id` is the stable Spall Spill Owner identity and is never replaced by `auth.users.id`.

### Provisioning

A progress record must exist for every Owner whose onboarding state can be resolved.

Existing Owners are backfilled by migration.

Future Owners receive their onboarding-progress record transactionally from application-controlled provisioning.

The initial step is:

`claim_handle`

The initial revision is:

`1`

### Progress truth

`current_step` is resumable account-side state.

Normal browser close, logout, device change, or session interruption must not intentionally reset acknowledged onboarding progress to S1.

A client-local value is not authoritative onboarding progress until the backend acknowledges it.

---

## 3. Primary Use Case

Canonical Primary Use Case values are:

- `creator`
- `affiliate`
- `business`
- `personal`
- `other`

The database representation is closed to these canonical values.

Primary Use Case is nullable before O01-S2 is completed.

Selecting a Primary Use Case:

- persists the value authoritatively;
- advances `current_step` from `primary_use_case` to `basic_identity`;
- increments the onboarding progress revision;
- does not create, delete, migrate, or restrict capability data.

Changing Primary Use Case later is allowed.

A later change must not silently delete downstream recoverable Identity/Product/Resource work.

---

## 4. Handle Identity Boundary

Handle is a mutable public locator.

Handle is not:

- `owner_id`;
- authentication identity;
- authorization identity;
- content ownership identity.

A Handle claim must always resolve ownership from the authenticated principal through the existing Auth-user → Owner binding.

Client-supplied `owner_id` is not accepted by the Handle mutation boundary.

---

## 5. Canonical Handle Representation

Handle comparison uses a normalized key.

For the MVP, accepted Handle input is intentionally conservative.

Normalization:

1. trim surrounding whitespace;
2. convert ASCII letters to lowercase;
3. validate the normalized result.

Canonical validation:

- length: 3 through 30 characters;
- allowed characters: ASCII `a-z`, `0-9`, `.`, `_`, `-`;
- first character must be ASCII alphanumeric;
- last character must be ASCII alphanumeric;
- unsupported Unicode forms are rejected rather than silently transliterated.

Display casing is not a separate identity in MVP.

The normalized Handle is the canonical public Handle representation used by this implementation.

Two inputs that normalize to the same value are the same namespace claim.

---

## 6. Reserved Handle Namespace

Reserved system routes and platform namespaces cannot be claimed as Owner Handles.

The initial reserved set must include at least:

- `api`
- `auth`
- `dashboard`
- `login`
- `signup`
- `recovery`
- `onboarding`
- `ops`
- `_next`
- `favicon.ico`
- `robots.txt`
- `sitemap.xml`

The reserved namespace is application-controlled and may be expanded without changing Owner identity semantics.

A reserved Handle is distinguishable from a malformed Handle and from an already-owned Handle.

---

## 7. Handle Namespace Persistence

Canonical namespace ownership is stored privately.

The persistence model must support both:

- one current canonical Handle per Owner;
- future protected historical aliases required by the locked Handle rename policy.

The namespace model therefore must not assume that an Owner can only ever have one Handle record for its entire lifetime.

For the initial S1 implementation:

- the first accepted claim becomes the Owner's current Handle;
- normalized Handle uniqueness is enforced atomically by PostgreSQL;
- merely typing/checking a candidate does not claim it;
- the Handle is claimed only on explicit Owner confirmation;
- while onboarding remains incomplete, the Owner may return to S1 and confirm a different valid available Handle;
- replacing the current onboarding Handle atomically converts the previous current Handle into a protected historical alias before the new Handle becomes current;
- a historical alias remains reserved to the same Owner and is not available for another Owner.

This onboarding correction path preserves the locked Handle continuity policy without implementing the recurring post-onboarding D09 rename workflow.

The recurring Handle-management UX remains deferred, but the namespace persistence model already preserves historical aliases correctly.

---

## 8. Claim Handle Mutation

The authoritative Handle-claim operation:

- requires an authenticated principal;
- resolves the canonical Owner from `auth.uid()`;
- accepts a candidate Handle;
- accepts the onboarding base revision;
- validates format;
- rejects reserved namespaces;
- enforces normalized uniqueness atomically;
- persists the current Handle;
- advances S1 to S2 when appropriate;
- increments progress revision;
- returns the acknowledged authoritative state.

The operation must be idempotent for the same Owner confirming the same already-current Handle.

The operation must never transfer a Handle owned by another Owner.

Expected semantic result classes include:

- `success`
- `invalid_handle`
- `reserved_handle`
- `handle_unavailable`
- `stale_write`
- `owner_missing`

Internal database errors remain generic application failures and are not converted into misleading validation states.

---

## 9. Primary Use Case Mutation

The authoritative Primary Use Case operation:

- requires an authenticated principal;
- resolves Owner authority from `auth.uid()`;
- accepts only a canonical Primary Use Case value;
- accepts the onboarding base revision;
- rejects stale writes;
- persists the new value;
- advances S2 to S3 when appropriate;
- increments the progress revision;
- returns acknowledged authoritative state.

The mutation accepts no target Owner identity.

---

## 10. Revision & Stale-Write Contract

Every persisted onboarding progress row has a monotonic revision.

Authoritative mutable writes use:

`base_revision = N`

and may commit only when:

`authoritative revision = N`

A successful mutation commits:

`revision = N + 1`

A stale mutation:

- returns a distinct `stale_write` result;
- changes no authoritative onboarding state;
- changes no Handle namespace state;
- must not be automatically retried as blind last-write-wins.

The client must refresh authoritative onboarding state before a new write is attempted.

This applies across tabs, devices, sessions, and out-of-order requests.

---

## 11. Read Boundary

The authenticated onboarding-state resolver returns only the current Owner's O01 state.

Minimum response:

- current semantic step;
- current canonical Handle, if claimed;
- Primary Use Case, if selected;
- progress revision.

It accepts no target Owner ID.

It does not expose another Owner's private onboarding state.

Public Handle availability/resolution is a separate concern from private onboarding-state retrieval.

---

## 12. Authorization & Database Exposure

Canonical tables remain in private internal schemas and receive no direct `anon` or `authenticated` table privileges.

Owner-facing mutation/read boundaries are narrow authenticated RPCs.

They derive caller identity from Supabase Auth and the existing `core.owner_auth_bindings` relation.

The caller cannot:

- choose another `owner_id`;
- modify another Owner's progress;
- modify another Owner's Handle;
- bypass Handle uniqueness;
- write `onboarding_completed_at`;
- directly mutate canonical private tables.

Functions use explicit grants and a fixed empty search path consistent with the existing database security baseline.

---

## 13. Onboarding Completion Boundary

S1 Handle claim is not onboarding completion.

S2 Primary Use Case selection is not onboarding completion.

Reaching S3, S4, S5, or S6 is not onboarding completion.

Preview is not onboarding completion.

A failed Publish is not onboarding completion.

This checkpoint does not write:

`core.owners.onboarding_completed_at`

That field remains exclusively governed by the later first-authoritative-publication implementation contract.
