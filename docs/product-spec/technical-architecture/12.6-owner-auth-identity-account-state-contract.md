# 12.6 — Owner Auth Identity & Account State Contract — LOCKED

## Decision status

- Status: **LOCKED / CURRENT OWNER-IDENTITY IMPLEMENTATION AUTHORITY**
- Stage: **12 — Technical Architecture**
- Resolves implementation details deferred by **OD-SEC-008**
- Depends on:
  - 11.1 authentication semantics;
  - 11.4 server ownership / authorization model;
  - 12.4 production technology/security architecture;
  - 12.5 authentication session and intended-destination contract.

This record defines the canonical database relationship between Supabase Auth principals and stable Spall Spill Owner identity.

It does not change J1–J9 user-flow topology.

---

## 1. Canonical identity separation

Supabase Auth and Spall Spill Owner identity are separate authorities.

Supabase:

- authenticates a principal;
- owns credentials, providers, identities, sessions, and authentication lifecycle.

Spall Spill:

- owns canonical Owner identity;
- owns account lifecycle/restriction state;
- owns onboarding completion state;
- owns product-data ownership and authorization.

Canonical relationship:

    Supabase auth.users.id
    ↓
    server-controlled Owner binding
    ↓
    stable Spall Spill ownerId

`auth.users.id` is not the Spall Spill product ownership key.

---

## 2. Stable Owner identifier

The canonical Spall Spill `ownerId` is an application-owned PostgreSQL UUID.

It:

- is generated independently from Supabase Auth identity;
- remains stable across Handle changes;
- remains stable across Display Name changes;
- remains stable across email changes;
- remains stable across safely linked authentication methods;
- remains stable across provider metadata changes.

The initial representation is PostgreSQL `uuid`.

---

## 3. Canonical Owner table

Canonical Owner records live in:

`core.owners`

Initial responsibilities are intentionally narrow:

- stable Owner ID;
- current account access state;
- onboarding-completion authority;
- record timestamps.

The Owner table does not store public Identity fields such as:

- Handle;
- Display Name;
- Bio;
- public profile photo;
- social links.

Those belong to later Identity implementation.

---

## 4. Account access state

Initial authoritative Owner access states are:

- `active`;
- `restricted`;
- `suspended`.

Normal newly provisioned Owners begin as `active`.

`restricted` and `suspended` take precedence over onboarding/navigation restoration.

Deletion semantics are not newly invented by this record. Missing, deleted, or otherwise unresolved Owner authority must fail closed until the dedicated deletion implementation is resolved.

---

## 5. Onboarding completion authority

Initial Owner state contains:

`onboarding_completed_at timestamptz null`

Semantics:

- `NULL` → onboarding is incomplete;
- non-NULL → onboarding has completed authoritatively.

Authentication metadata cannot set this field.

Successful Sign Up or Login does not complete onboarding.

Detailed resumable onboarding progress remains Stage 6 work.

---

## 6. Auth binding table

The authoritative principal-to-Owner relationship lives in:

`core.owner_auth_bindings`

Initial relationship:

- `auth_user_id` references the primary key `auth.users.id`;
- `owner_id` references `core.owners.id`;
- one Supabase Auth user may resolve to exactly one canonical Owner;
- one canonical Owner may have more than one authoritative Auth binding if a future controlled credential migration/recovery requires it.

Normal Supabase identity linking usually keeps Email/Password and Google identities underneath one `auth.users.id`.

Spall Spill does not bind ownership to `auth.identities.id`, provider ID, or email text.

---

## 7. Auth-user deletion behavior

Deleting a Supabase Auth user removes that Auth binding.

It does not automatically delete the canonical Spall Spill Owner record or product ownership graph.

This preserves separation between credential/authentication lifecycle and product-account lifecycle.

Any later Owner deletion workflow must be explicit and authoritative.

---

## 8. Provisioning

A newly created Supabase Auth user is provisioned with:

1. one new canonical `core.owners` row;
2. one `core.owner_auth_bindings` row connecting `auth.users.id` to the new Owner.

Provisioning occurs transactionally through a PostgreSQL `AFTER INSERT` trigger on `auth.users`.

The trigger must:

- use no client-supplied Owner ID;
- use no email matching;
- use no `raw_user_meta_data` authorization value;
- use no provider profile metadata;
- create no public Identity content;
- complete no onboarding step.

A provisioning failure is treated as an authentication/account-creation failure and must be tested through the real local Supabase Auth API.

---

## 9. Trigger security

The provisioning trigger function:

- lives in the private `core` schema;
- is `SECURITY DEFINER` only because it executes from the Supabase-managed Auth insertion boundary into private application tables;
- uses an empty fixed `search_path`;
- references application tables with fully qualified names;
- receives no arbitrary SQL identifier or dynamic SQL;
- has executable access revoked from `PUBLIC`, `anon`, and `authenticated`.

The trigger capability is not exposed as a normal client RPC.

---

## 10. Metadata boundary

Neither of these is product authorization authority:

- `raw_user_meta_data`;
- `user_metadata`.

Provider names, avatars, names, email text, and other authentication metadata must not determine:

- Owner ID;
- account restriction state;
- onboarding completion;
- ownership;
- Operator capability;
- Published Identity.

`raw_app_meta_data` / JWT claims also do not replace the canonical Owner binding and current database authorization state.

---

## 11. RLS and schema exposure

`core.owners` and `core.owner_auth_bindings` remain private canonical tables.

Both tables use Row Level Security as defense in depth.

No direct `anon` or `authenticated` table access is granted.

The `core` schema remains unavailable to normal Data API clients.

Later Owner-state resolution is exposed only through a narrowly scoped server-safe API/view/function contract.

---

## 12. Resolver input

The future owner-state resolver starts from a verified Supabase Auth user ID and resolves:

    verified auth user
    ↓
    owner_auth_bindings
    ↓
    core.owners
    ↓
    account state
    ↓
    onboarding completion
    ↓
    resolver destination decision

Authentication alone never synthesizes a missing Owner record as Active.

Missing or ambiguous binding fails closed.

---

## 13. Ownership of future entities

Future Owner-scoped entities use `core.owners.id` as their ownership foreign key.

They do not use:

- email;
- Handle;
- provider ID;
- `auth.identities.id`;
- client-supplied owner identity.

Server/database authorization resolves the current principal to `ownerId` before consequential private reads or writes.

---

## 14. Multiple authentication methods

Supabase Auth may associate multiple identities with one Auth user.

When that occurs:

    Email identity
    +
    Google identity
    ↓
    same auth.users.id
    ↓
    same owner_auth_bindings row
    ↓
    same ownerId

Authentication-method linking therefore does not recreate Spall Spill ownership.

Unsafe automatic Owner merging based only on matching email text is forbidden.

---

## 15. Initial database shape

The first implementation consists conceptually of:

- enum `core.owner_account_state`;
- table `core.owners`;
- table `core.owner_auth_bindings`;
- private provisioning trigger function;
- `AFTER INSERT` trigger on `auth.users`;
- RLS enabled on both application tables;
- explicit privilege revocations;
- indexes required for authoritative Owner lookup.

No public profile, Handle, Product, Spill, Resource, analytics, or Operator table is introduced by this lock.

---

## 16. Test contract

Minimum database/runtime verification includes:

1. Owner table exists.
2. Auth-binding table exists.
3. Owner ID is independent from Auth user ID.
4. New Supabase Auth signup creates exactly one Owner.
5. New Supabase Auth signup creates exactly one binding.
6. Binding points to the created Owner.
7. New Owner is `active`.
8. New Owner has incomplete onboarding.
9. Client roles cannot directly use private Owner tables.
10. Forged email/provider metadata cannot select another Owner.
11. Deleting an Auth user cannot transfer ownership to another user.
12. Duplicate direct binding for one Auth user is rejected.
13. Unknown Auth user resolves to no Owner authority.
14. Trigger function is not exposed as a normal client-callable capability.

---

## 17. Locked decisions

1. Spall Spill `ownerId` is distinct from Supabase `auth.users.id`.
2. `ownerId` uses application-owned PostgreSQL UUID.
3. Canonical Owner state lives in `core.owners`.
4. Auth-to-Owner mapping lives in `core.owner_auth_bindings`.
5. Binding references the primary key `auth.users.id`.
6. Each Auth user resolves to at most one canonical Owner.
7. One Owner may support multiple controlled Auth bindings in the future.
8. Email text is never an ownership binding.
9. Handle is never an ownership binding.
10. Provider identity metadata is never ownership authority.
11. `raw_user_meta_data` is never authorization authority.
12. New Owner access state defaults to `active`.
13. Initial restrictive account states are `restricted` and `suspended`.
14. Onboarding completion is authoritative database state.
15. Auth success does not complete onboarding.
16. New Auth users receive transactional Owner provisioning.
17. Provisioning uses an `AFTER INSERT` trigger on `auth.users`.
18. Provisioning creates no public Identity content.
19. Provisioning does not depend on user/provider metadata.
20. Trigger function is private, narrowly privileged, and uses fixed empty `search_path`.
21. `core.owners` and `core.owner_auth_bindings` remain private.
22. RLS is enabled as defense in depth.
23. Normal clients receive no direct access to these tables.
24. Future owned product records reference `ownerId`, not Auth/provider/email identifiers.
25. Missing or ambiguous Owner binding fails closed.
26. Auth-user deletion does not silently delete or transfer canonical product ownership.
27. Multiple safely linked Supabase identities preserve the same Owner.
28. Owner-state resolver reads authoritative current database state after authentication.
