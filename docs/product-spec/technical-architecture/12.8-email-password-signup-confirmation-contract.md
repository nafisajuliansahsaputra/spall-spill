# 12.8 — Email/Password Sign Up & Confirmation Contract — LOCKED

## Decision status

- Status: **LOCKED / CURRENT EMAIL-PASSWORD SIGNUP AUTHORITY**
- Stage: **12 — Technical Architecture**
- Surface: **A01 Sign Up / Create Account**
- Depends on:
  - 12.5 Authentication Session & Intended-Destination Contract;
  - 12.6 Owner Auth Identity & Account State Contract;
  - 12.7 Owner-State Resolver Contract;
  - locked A01 Sign Up / Create Account UX semantics.

This record defines the production Email/Password account-creation and email-confirmation behavior for Spall Spill.

It does not redefine Google OAuth, Login, Recovery, onboarding content, or action-level authorization.

---

## 1. Authentication method

MVP Email/Password Sign Up uses Supabase Auth.

Canonical account-creation call:

`supabase.auth.signUp(...)`

Application code does not create rows directly inside `auth.users`.

Canonical Spall Spill Owner provisioning remains the database-owned Auth-user provisioning boundary defined in 12.6.

---

## 2. Email confirmation requirement

Production Email/Password Sign Up requires confirmation of the supplied email address before the new authentication relationship may be used as a normal authenticated Owner session.

Canonical rule:

> Email/Password registration may create the Auth user and stable Owner binding before confirmation, but protected Owner access begins only after authoritative email confirmation establishes a valid session.

An unconfirmed signup does not create:

- public Identity;
- public Handle;
- Spill content;
- Product;
- Resource;
- publication state;
- Platform Activation;
- Spill Activation;
- Commerce Activation.

---

## 3. Local-development parity

Source-controlled local Supabase Auth configuration mirrors the production confirmation requirement.

Local development therefore uses:

`auth.email.enable_confirmations = true`

Mailpit is the canonical local email-capture mechanism.

Tests must not depend on disabling confirmation merely to make signup easier.

Where a low-level database test requires direct Auth fixtures, it may continue using controlled database fixtures independent of the user-facing email flow.

---

## 4. SSR / PKCE confirmation model

Spall Spill uses the Supabase SSR/PKCE-compatible email confirmation flow.

The canonical internal confirmation endpoint is:

`/auth/confirm`

Confirmation email links deliver only the verification material required by Supabase Auth.

The application exchanges the token hash through:

`supabase.auth.verifyOtp(...)`

before treating confirmation as successful.

---

## 5. Confirmation URL authority

The signup confirmation endpoint is fixed application infrastructure.

A caller cannot provide an arbitrary final redirect URL.

The confirmation flow does not use a user-controlled:

- origin;
- host;
- external URL;
- `next` URL;
- intended-destination query parameter.

Final navigation is determined by current Spall Spill Owner state after successful verification.

---

## 6. Intended-destination separation

The email confirmation URL does not serialize the intended Owner destination.

Same-browser intended navigation remains in:

`spall_intended_destination`

according to 12.5.

Therefore:

- authentication verification data stays in the confirmation flow;
- navigation context stays in the dedicated HttpOnly intended-destination cookie;
- neither becomes authority for the other.

---

## 7. Confirmation token boundary

The confirmation token hash is security-sensitive authentication material.

It must never be:

- copied into the intended-destination cookie;
- persisted in ordinary application state;
- emitted into general analytics;
- intentionally logged;
- exposed in a final post-auth navigation URL;
- used as Owner authorization.

The confirmation handler removes authentication verification parameters from the final navigation surface.

---

## 8. Sign Up inputs

Initial Email/Password A01 collects only:

- email;
- password.

A01 does not collect:

- Handle;
- Display Name;
- Bio;
- profile image;
- Primary Use Case;
- Product;
- Resource;
- marketplace information;
- public-page configuration.

Those remain onboarding or later workspace responsibilities.

---

## 9. Password baseline

Initial application password minimum is:

`8 characters`

Source-controlled local Supabase configuration must enforce at least the same minimum.

The application may provide stronger password guidance without inventing arbitrary complexity requirements.

Passwords are never:

- logged;
- stored by Spall Spill application tables;
- persisted in analytics;
- copied into URL/query state;
- copied into intended-destination state.

Supabase Auth remains password-storage authority.

---

## 10. Sign Up submission

Email/Password account creation is performed through trusted application Auth infrastructure.

Submission rules:

- validate input before provider call;
- prevent accidental duplicate execution while pending;
- call Supabase Auth once per accepted submission;
- do not manually create Owner rows from the application;
- do not accept client-supplied Owner identity;
- do not claim success before the provider response is authoritative.

---

## 11. Confirmation-pending result

When signup succeeds but no authenticated session is established because confirmation is required, A01 enters a confirmation-pending state.

The user receives safe guidance to check the supplied email.

Confirmation-pending is not:

- onboarding completion;
- authenticated Owner Workspace access;
- public activation;
- publication success.

---

## 12. Account enumeration boundary

Sign Up UX must not unnecessarily reveal whether a supplied email already owns an account.

Provider responses that intentionally obscure account existence remain obscured.

Application copy must not convert provider anti-enumeration behavior into a reliable account-discovery oracle.

Where appropriate, the user may be guided generically toward:

- checking email;
- Login;
- Recovery.

---

## 13. Failed Sign Up

Validation, provider, network, rate-limit, anti-abuse, or infrastructure failure never becomes successful registration.

Safe local field feedback may be returned.

Sensitive provider details, tokens, credentials, stack traces, and internal security state are not shown to the user.

---

## 14. Confirmation processing

`/auth/confirm` accepts only the expected Supabase email verification material required for the supported confirmation operation.

Malformed, missing, invalid, or expired verification material fails closed.

Failure:

- does not authenticate;
- does not activate an Owner;
- does not consume arbitrary intended navigation;
- does not redirect externally.

The user returns to a safe authentication surface with generic recovery guidance.

---

## 15. Owner-state resolution after confirmation

After successful verification and session establishment, the application runs the canonical Owner-state resolver.

Canonical precedence remains:

1. `restricted` → D10.
2. `suspended` → D10.
3. `onboarding_incomplete` → O01.
4. `active`:
   - valid current authorized intended destination → intended destination;
   - otherwise → D01.
5. `owner_missing` → controlled fail-closed account-state handling.

The intended destination never precedes Owner-state resolution.

---

## 16. Genuine new account

Normal genuine Email/Password Sign Up flow is:

```text
A01
→ submit email/password
→ Auth user provisioned
→ Owner binding provisioned
→ confirmation pending
→ user confirms email
→ session established
→ Owner-state resolver
→ onboarding_incomplete
→ O01
