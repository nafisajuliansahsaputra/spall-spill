# 12.16 — Onboarding preview receipt — LOCKED

This bounded technical contract extends 12.15 and pinned O01-S6's mandatory
review-before-first-Publish rule. It does not enable or close first publication.

The Owner explicitly confirms the displayed private preview. The authenticated
current-Owner RPC receives only the displayed snapshot digest. The database
locks Owner then onboarding progress, re-resolves current S6 prerequisites and
the full saved snapshot, and rejects malformed or changed digests before writing.
No caller-provided Owner, content, safety verdict or publication eligibility is
trusted. Account/session and S6 eligibility are repeated at confirmation.

One private receipt row per Owner bounds storage and represents the latest
confirmed snapshot. It stores an unpredictable UUID, SHA-256 digest, issued time
and fixed ten-minute expiry. Reconfirming the same unexpired digest reuses the
receipt without extending expiry. A new digest or expired receipt rotates its
UUID; superseded tokens cannot represent the current confirmation. Stale or
invalid confirmation leaves a valid existing receipt untouched. Concurrent
confirmations serialize under the shared Owner-first lock order.

Receipt rows have RLS, no Data API table grants and no anonymous/service-role
function grant. The RPC derives Owner from auth.uid() and exposes only that
Owner's acknowledgment. The client verifies exact digest binding, UUID and a
future expiry before showing confirmation. Confirming creates no public state,
Item, Draft, progress change, onboarding completion or analytics event.

Confirmation is review evidence, not permission to publish invalid content.
The future first-Publish transaction must verify current Owner, matching live
receipt UUID and digest, repeat a fresh snapshot under content/safety locks,
reject stale/expired/unsafe state, validate an explicit Identity-only or selected
Item bundle, and commit publication/completion/idempotency atomically. The
receipt alone never authorizes another Owner, bypasses safety, or proves that
all external providers and public-media transport are ready.

The UI offers Confirm this preview and reports private confirmation separately
from publication. Missing/failed confirmation retains saved Working and Drafts.
No Publish success is shown by this checkpoint. Changing the rendered snapshot
resets local confirmation state; future Publish must still check the database.
