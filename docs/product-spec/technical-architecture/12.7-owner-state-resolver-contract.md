# 12.7 — Owner-State Resolver Contract — LOCKED

## Decision status

- Status: **LOCKED / CURRENT OWNER-STATE RESOLUTION AUTHORITY**
- Stage: **12 — Technical Architecture**
- Depends on:
  - 12.4 Production Technology Stack & Security Architecture;
  - 12.5 Authentication Session & Intended-Destination Contract;
  - 12.6 Owner Auth Identity & Account State Contract.

This record defines how a verified Supabase authentication principal is resolved into current authoritative Spall Spill Owner state.

It does not implement Login, Sign Up, Recovery, intended-destination persistence, or final route redirects.

---

## 1. Purpose

The Owner-state resolver answers one question:

> Given the current authenticated principal, what authoritative Spall Spill Owner state exists right now?

It does not decide authentication credentials.

It does not trust client-provided Owner identity.

It does not grant content authorization merely because an Owner record exists.

---

## 2. Canonical resolution chain

The canonical chain is:

    verified Supabase Auth principal
    ↓
    current auth user identity
    ↓
    core.owner_auth_bindings
    ↓
    core.owners
    ↓
    account_state
    ↓
    onboarding_completed_at
    ↓
    typed Owner-state resolution

The resolver never uses:

- email matching;
- Handle matching;
- provider profile metadata;
- raw_user_meta_data;
- user_metadata;
- client-supplied ownerId;
- client-supplied auth user ID.

---

## 3. Authentication proof boundary

Application server code verifies the current authentication relationship with:

`supabase.auth.getClaims()`

before treating the request as authenticated.

`getSession()` is not used as identity proof.

A missing valid authenticated claim resolves as:

`unauthenticated`

The database resolver independently derives the current Auth identity from the authenticated request context.

---

## 4. Database interface

The canonical database interface is:

`api.resolve_current_owner_state()`

It accepts **zero arguments**.

The function derives the current Supabase Auth user from:

`auth.uid()`

This prevents a caller from selecting another user by passing:

- another Auth user UUID;
- another Owner UUID;
- email;
- Handle;
- provider ID;
- arbitrary ownership input.

---

## 5. Dedicated API schema

The existing `api` schema becomes the explicit narrow Data API surface for safe application RPC interfaces.

Initial exposure rule:

- `api` may be exposed through Supabase Data API;
- `authenticated` receives `USAGE` on `api`;
- `anon` does not receive `USAGE`;
- internal schemas such as `core`, `moderation`, `audit`, `ops`, and other canonical schemas remain unavailable to normal application roles unless separately justified;
- exposing `api` does not expose `core`.

Every object inside `api` still requires explicit object-level grants.

Schema exposure is not permission by itself.

---

## 6. Resolver function security

`api.resolve_current_owner_state()` is:

- `SECURITY DEFINER`;
- fixed to an empty `search_path`;
- fully schema-qualified internally;
- read-only in product semantics;
- zero-argument;
- executable by `authenticated`;
- not executable by `anon`;
- not executable by `PUBLIC`.

`SECURITY DEFINER` exists only to allow the narrow resolver to read private canonical Owner tables without granting those tables directly to normal application roles.

---

## 7. Resolver return contract

The database function returns one JSON object.

Canonical keys are:

- `status`;
- `owner_id`;
- `account_state`;
- `onboarding_completed`.

The response contains no:

- email;
- password information;
- provider token;
- authentication secret;
- public profile content;
- moderation evidence;
- Operator capability;
- arbitrary private Owner record.

---

## 8. Canonical statuses

The resolver supports exactly these initial statuses:

1. `unauthenticated`
2. `owner_missing`
3. `restricted`
4. `suspended`
5. `onboarding_incomplete`
6. `active`

Meaning:

### unauthenticated

No usable authenticated Supabase principal is present.

No Owner authority exists.

### owner_missing

An authenticated principal exists but no valid canonical Owner binding can be resolved.

This fails closed.

The application must not synthesize a new Active Owner during ordinary Login/navigation resolution.

### restricted

A canonical Owner exists with:

`account_state = restricted`

Restriction takes precedence over onboarding completion and intended destination.

### suspended

A canonical Owner exists with:

`account_state = suspended`

Suspension takes precedence over onboarding completion and intended destination.

### onboarding_incomplete

A canonical Owner exists with:

- `account_state = active`;
- `onboarding_completed_at IS NULL`.

### active

A canonical Owner exists with:

- `account_state = active`;
- `onboarding_completed_at IS NOT NULL`.

`active` therefore means Active + onboarding complete for resolver purposes.

---

## 9. Resolver precedence

Canonical database resolution precedence is:

1. no authenticated principal → `unauthenticated`;
2. no authoritative Owner binding → `owner_missing`;
3. `restricted` → `restricted`;
4. `suspended` → `suspended`;
5. Active + onboarding incomplete → `onboarding_incomplete`;
6. Active + onboarding complete → `active`.

No intended-destination value participates in determining these states.

---

## 10. Navigation mapping

Final navigation remains application-layer responsibility.

Canonical later mapping is:

    unauthenticated
    → A02 / authentication flow as appropriate

    owner_missing
    → fail closed / controlled account-state failure handling

    restricted
    → D10

    suspended
    → D10

    onboarding_incomplete
    → O01

    active
    → valid authorized intended destination
      otherwise D01

This record does not yet implement those redirects.

---

## 11. Intended-destination separation

The Owner-state resolver does not:

- read the intended-destination cookie;
- validate intended destination;
- consume intended destination;
- redirect to intended destination.

That remains the next implementation layer.

Owner state is resolved first.

---

## 12. Stable Owner ID

Successful Owner resolutions may return:

`owner_id`

This is the stable application-owned `core.owners.id`.

`owner_id` is not itself an authorization token.

Possession or observation of an Owner UUID cannot grant authority.

Consequential reads and writes still perform current authorization.

---

## 13. Account state source

The resolver reads current:

`core.owners.account_state`

It does not cache account state inside:

- user metadata;
- JWT user metadata;
- browser storage;
- client state;
- intended-destination state.

Current database state remains authoritative.

---

## 14. Onboarding source

The resolver reads current:

`core.owners.onboarding_completed_at`

Semantics remain:

- NULL → incomplete;
- non-NULL → complete.

Auth success does not modify this field.

Resolver execution does not modify this field.

---

## 15. Missing binding behavior

A valid authentication session without a valid Owner binding must fail closed.

The resolver must not automatically:

- create an Owner;
- repair ownership;
- match by email;
- match by provider identity;
- merge accounts;
- claim an existing Owner.

Normal Owner creation remains the transactional Auth provisioning boundary defined in 12.6.

Repair/recovery of a genuinely broken mapping is a separate controlled operational concern.

---

## 16. Ambiguity behavior

The database schema currently guarantees one Auth user resolves to at most one Owner through the primary-key constraint on `auth_user_id`.

If future schema evolution ever permits an ambiguous authoritative relationship, ambiguity must fail closed.

The application must never choose an arbitrary Owner row.

---

## 17. Infrastructure failure

Database/API infrastructure failure is not a normal Owner state.

The application wrapper must not map:

- RPC failure;
- malformed resolver payload;
- network failure;
- unexpected database response

to `active`.

Infrastructure failures must surface as controlled errors and remain fail closed.

---

## 18. Application wrapper

The canonical Next.js server helper will:

1. create a request-scoped Supabase server client;
2. verify authentication using `getClaims()`;
3. return `unauthenticated` when no verified authenticated principal is available;
4. invoke `api.resolve_current_owner_state()` for authenticated requests;
5. validate the returned payload;
6. convert it into a typed application union;
7. throw/fail closed on malformed or infrastructure failure.

The helper is server-side application infrastructure.

---

## 19. Typed application result

The initial application result family is conceptually:

    { status: "unauthenticated" }

    { status: "owner_missing" }

    {
      status: "restricted",
      ownerId: string
    }

    {
      status: "suspended",
      ownerId: string
    }

    {
      status: "onboarding_incomplete",
      ownerId: string
    }

    {
      status: "active",
      ownerId: string
    }

`ownerId` is required for all successfully resolved canonical Owner states.

---

## 20. Client-access safety

The application intends to call the resolver from server-side Owner flows.

However, database security must remain safe even if an authenticated client calls the RPC directly.

Therefore the RPC:

- accepts no target identity;
- derives `auth.uid()` internally;
- returns only the caller's own narrow state;
- cannot mutate Owner state;
- cannot expose another Owner through parameters.

Security does not depend on hiding the RPC name.

---

## 21. Authorization boundary

Owner-state resolution is not sufficient authorization for:

- editing Identity;
- editing Spill;
- publishing;
- deleting;
- analytics access;
- moderation operations;
- Operator actions;
- another Owner's resources.

Those operations require their own current server/data-layer authorization.

Canonical invariant remains:

> Authentication ≠ Owner resolution ≠ action authorization.

---

## 22. Logging boundary

The resolver does not emit ordinary product analytics.

Do not log:

- authentication tokens;
- raw JWT;
- cookies;
- provider secrets;
- full RPC payloads containing security artifacts.

Owner-state failures may later emit sanitized operational telemetry where justified.

---

## 23. Database tests

Minimum database verification includes:

1. `api` remains inaccessible to `anon`.
2. `authenticated` has `USAGE` on `api`.
3. resolver function exists.
4. resolver accepts zero arguments.
5. resolver is `SECURITY DEFINER`.
6. resolver has fixed empty `search_path`.
7. PUBLIC cannot execute resolver.
8. anon cannot execute resolver.
9. authenticated can execute resolver.
10. unauthenticated database context returns `unauthenticated`.
11. unknown Auth identity returns `owner_missing`.
12. Active + incomplete Owner returns `onboarding_incomplete`.
13. Active + complete Owner returns `active`.
14. restricted Owner returns `restricted` regardless of onboarding state.
15. suspended Owner returns `suspended` regardless of onboarding state.
16. returned Owner ID matches the canonical binding.
17. resolver exposes no cross-Owner target parameter.
18. private `core` tables remain inaccessible directly to normal client roles.

---

## 24. Application tests

Minimum application-side verification includes:

1. no verified claims → `unauthenticated`;
2. authenticated resolver payload parses into the correct typed status;
3. malformed payload fails closed;
4. RPC error does not become Active;
5. restricted/suspended result retains stable Owner ID;
6. onboarding-incomplete result retains stable Owner ID;
7. Active result requires valid Owner ID;
8. helper does not use `getSession()` as identity proof.

---

## 25. Deployment configuration boundary

Because the resolver lives in the dedicated `api` schema, production Supabase Data API configuration must include `api` in its exposed-schema configuration before this RPC is used in production.

Source-controlled local Supabase configuration must represent the same intended schema exposure.

This does not grant object privileges automatically.

## 28. Locked decisions

1. Owner state is resolved only after authoritative authentication proof.
2. Application authentication proof uses `getClaims()`.
3. `getSession()` is not identity proof.
4. Canonical resolver RPC is `api.resolve_current_owner_state()`.
5. Resolver accepts zero arguments.
6. Resolver derives the Auth principal from `auth.uid()`.
7. Client-supplied Owner/Auth identifiers are forbidden resolver inputs.
8. `api` becomes the dedicated narrow Data API schema.
9. `api` exposure does not expose `core`.
10. `anon` receives no `api` schema usage.
11. `authenticated` receives only explicitly required `api` access.
12. Resolver function is `SECURITY DEFINER`.
13. Resolver function uses fixed empty `search_path`.
14. Resolver object privileges are explicitly granted/revoked.
15. Resolver returns one narrow JSON object.
16. Initial statuses are unauthenticated, owner_missing, restricted, suspended, onboarding_incomplete, and active.
17. Missing binding fails closed.
18. Resolver never repairs or synthesizes Owner authority.
19. restricted and suspended take precedence over onboarding.
20. onboarding incomplete applies only to Active Owners.
21. active resolver status means Active + onboarding complete.
22. Intended destination is not read or consumed by this resolver.
23. Stable ownerId may be returned but is never authority by possession.
24. Current database account state is authoritative.
25. Current database onboarding state is authoritative.
26. Infrastructure or malformed responses never become Active.
27. Final navigation mapping remains application-layer responsibility.
28. Resolver safety must hold even if an authenticated client calls the RPC directly.
