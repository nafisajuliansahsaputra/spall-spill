# 12.5 — Authentication Session & Intended-Destination Contract — LOCKED

## Decision status

- Status: **LOCKED / CURRENT AUTH IMPLEMENTATION AUTHORITY**
- Stage: **12 — Technical Architecture**
- Resolves: **OD-SEC-003 — Intended-Destination Storage / Transport / Safety**
- Depends on:
  - locked A01 Sign Up semantics;
  - locked A02 Login / re-authentication semantics;
  - locked A03 Recovery semantics;
  - locked owner-state resolver;
  - locked authentication ≠ authorization invariant;
  - `12.4-production-technology-stack-security-architecture.md`.

This record defines the implementation contract for Owner authentication-session transport and safe restoration of an interrupted protected Owner destination.

### Server Action navigation repair — 2026-10-05

Password Login resolves the authoritative final internal destination in the same
request and redirects directly there. Redirecting a Server Action to the GET-only
`/auth/resolve` handler can render its downstream page while retaining that URL;
the next form POST then returns 405. Both entry points share one server-only
destination decision, including Owner checks, intended-cookie consumption/clearing,
and fail-closed failures. Provider callbacks keep normal HTTP navigation through
the GET handler. Account eligibility and destination-sanitization rules stay intact.

It does not change J1–J9 user-flow topology.

> Intended destination restores navigation only. It never grants authority.

---

## 1. Authentication authority

The production authentication provider is **Supabase Auth**.

MVP Owner authentication methods are:

- Email + Password;
- Google OAuth.

Historical Firebase authentication decisions are superseded where they conflict with current Stage 12 technology authority.

Authentication remains separate from stable Spall Spill Owner identity and from authorization.

---

## 2. Next.js SSR session model

The web application uses:

- `@supabase/supabase-js`;
- `@supabase/ssr`;
- cookie-based Supabase SSR sessions;
- PKCE-compatible authentication flows;
- request-scoped Supabase server clients;
- Next.js Proxy for normal authentication-token refresh.

A Supabase server client must not be stored in module-global mutable state or reused across unrelated requests.

---

## 3. Server authentication proof

Protected server behavior must not trust client-visible session state as authorization authority.

Normal Next.js Proxy session maintenance uses `supabase.auth.getClaims()`.

Server-side protection must not trust `supabase.auth.getSession()` as proof of authenticated identity.

`getSession()` may be used later only when raw session/token material is specifically required. Its embedded user object is not authorization authority.

Current Spall Spill authorization still requires authoritative application and database checks.

---

## 4. Session refresh response safety

When `@supabase/ssr` refreshes authentication state and returns cookies and cache headers through its `setAll` callback, the Next.js Proxy must preserve:

- refreshed cookies;
- `Cache-Control`;
- `Expires`;
- `Pragma`;
- other required response headers supplied by the SSR library.

Responses containing refreshed authentication cookies must not be reused as cross-user cached authenticated responses.

---

## 5. Session persistence

Normal Owner authentication remains persistent on the same browser/device while the authoritative Supabase authentication relationship remains valid.

Short-lived token refresh happens transparently.

Spall Spill does not impose an arbitrary short routine idle logout solely to force repeated Login ceremony.

Explicit Sign Out ends the current browser/device authentication state according to the provider/session contract.

---

## 6. Intended-destination purpose

An intended destination exists only to restore Owner navigation after authentication, re-authentication, or Recovery interrupts a valid protected Owner workflow.

It is not:

- an authorization token;
- ownership proof;
- pending mutation;
- permission grant;
- account-state override;
- arbitrary redirect mechanism.

Canonical invariant:

**intended destination = navigation context only**

---

## 7. Intended-destination cookie

Normal Owner intended destination is stored in a dedicated short-lived server-managed cookie.

Initial cookie contract:

- Name: `spall_intended_destination`
- HttpOnly: `true`
- SameSite: `Lax`
- Secure: `true` in production
- Path: `/`
- Domain: not explicitly set
- Max-Age: `1800` seconds / 30 minutes

This cookie is separate from Supabase authentication cookies.

Spall Spill does not manually redefine Supabase Auth cookie internals through this contract.

---

## 8. Allowed value

The stored value must be a sanitized internal relative pathname.

Initial supported protected Owner route family:

- `/dashboard`
- `/dashboard/*`

Examples of potentially valid values:

- `/dashboard`
- `/dashboard/spill`
- `/dashboard/identity`

The value must not contain an origin, host, scheme, credentials, or external URL.

---

## 9. Query-state boundary

Until a surface has a separately locked canonical safe query-state schema, intended-destination persistence stores pathname only.

Raw or arbitrary query parameters are not persisted merely for convenience.

A future safe query-state contract may permit explicitly approved non-sensitive query state without reopening the core intended-destination model.

---

## 10. Rejected destinations

An intended destination is rejected if it is:

- absolute;
- protocol-relative;
- external;
- malformed;
- outside the approved protected route family;
- encoded to escape the approved route family;
- carrying control characters;
- stale;
- expired;
- incompatible with current account state;
- no longer authorized for the authenticated Owner.

Examples that must be rejected include:

- `https://evil.example`
- `//evil.example`
- `javascript:...`
- `/dashboard/../../external`

Invalid intent falls back through the normal owner-state resolver.

---

## 11. Sensitive-data exclusion

The intended-destination cookie must never contain:

- password;
- access token;
- refresh token;
- OAuth authorization code;
- OAuth secret;
- email-verification token;
- password-recovery token;
- challenge/CAPTCHA artifact;
- raw credential material;
- sensitive mutation payload;
- private form contents;
- authorization decisions.

Security artifacts also remain excluded from ordinary analytics and product logs.

---

## 12. Resolver precedence

Successful authentication or Recovery enters the authoritative owner-state resolver before intended navigation is restored.

Canonical precedence:

1. Suspended or restricted → D10.
2. Else onboarding incomplete → O01.
3. Else Active + onboarding complete:
   - valid, current, authorized intended destination → intended destination;
   - otherwise → D01.

An intended destination cannot bypass D10 or O01.

---

## 13. Authorization after restoration

Even a syntactically valid intended destination grants no access by itself.

Allowed protected behavior requires all relevant authority to remain valid:

- authenticated identity;
- current Spall Spill Owner/account state;
- server/data-layer authorization;
- target ownership or permission;
- current target state.

Changing a cookie, URL, route parameter, object ID, or client state cannot create Owner authority.

---

## 14. Single-use lifecycle

A successfully consumed intended destination is cleared after resolver handling.

Invalid or expired intent is also cleared where appropriate.

The cookie is not retained indefinitely as sticky navigation history.

A new protected-auth interruption may replace a prior pending navigation intent with the currently relevant valid intent.

---

## 15. Google OAuth callback

Google OAuth uses a fixed internal application callback:

- `/auth/callback`

The provider callback does not accept an arbitrary final return URL.

The callback establishes or exchanges the authenticated session and then enters the normal owner-state resolver.

Final Owner navigation comes from trusted application context, not an attacker-controlled OAuth redirect target.

---

## 16. Email/Password behavior

Email/Password Login establishes authoritative Supabase authentication state and then enters the same owner-state resolver.

Login success must not blindly hardcode `/dashboard` when:

- account state requires D10;
- onboarding state requires O01;
- a valid authorized intended destination should be restored.

---

## 17. Recovery behavior

Recovery may preserve the same safe intended navigation context when it occurs in the same browser context and the intent remains valid.

If:

- Recovery occurs on another browser/device;
- the cookie expires;
- the destination becomes invalid;
- authorization changes;

successful Recovery falls back through the normal resolver.

Recovery itself is not considered failed merely because an old intended destination cannot be restored.

---

## 18. Re-authentication boundary

Security-sensitive re-authentication may preserve navigation context using the same safe principles.

Pending protected mutation payloads must not be serialized into the ordinary intended-destination cookie.

A later action-specific re-auth implementation may use opaque protected server-side context where necessary.

After re-authentication:

1. restore protected context;
2. re-read authoritative state;
3. re-check permission;
4. re-check target/revision;
5. execute only after explicit current intent.

Successful re-authentication never automatically executes a previously pending mutation.

---

## 19. Public-route boundary

Public P01–P04 remain anonymous.

The presence or absence of an authentication session does not create a Login gate for valid Published public content.

The intended-destination mechanism exists for protected Owner navigation, not public audience navigation.

---

## 20. Operator boundary

The initial Owner intended-destination allowlist does not include `/ops/*`.

Operator access has separate stronger-authentication and permission requirements.

Operator navigation may reuse suitable security primitives later but does not silently inherit normal Owner authority.

---

## 21. Logging and analytics

Raw intended-destination values are not emitted into general analytics by default.

If navigation restoration later requires measurement, use sanitized route classes or approved non-sensitive identifiers rather than raw sensitive URLs.

Authentication credentials, tokens, codes, and recovery artifacts are never analytics payload.

---

## 22. Failure behavior

If intended-destination validation fails:

- do not redirect externally;
- do not reveal protected target existence unnecessarily;
- do not grant authority;
- do not fail authentication itself;
- clear or reject unsafe intent;
- continue through safe resolver fallback.

Navigation-context failure remains distinct from authentication failure.

---

## 23. Implementation sequence

The authorized Auth implementation order is:

1. Supabase SSR dependencies.
2. Browser/server Supabase client utilities.
3. Next.js Proxy session-refresh foundation.
4. Environment contract.
5. Stable Spall Spill Owner/auth mapping.
6. Owner-state resolver.
7. Intended-destination helper/cookie implementation.
8. A01 Sign Up.
9. A02 Login.
10. Google OAuth callback.
11. A03 Recovery.
12. Sign Out.
13. Authentication/authorization tests.

Database ownership and lifecycle state must exist before the resolver claims to know whether an Owner is Active, Suspended, restricted, or onboarding-complete.

---

## 24. Locked decisions

1. Supabase Auth is current production authentication authority.
2. MVP methods are Email/Password and Google OAuth.
3. `@supabase/ssr` owns cookie-based Next.js SSR session integration.
4. Server clients are request-scoped.
5. Next.js Proxy maintains normal token refresh.
6. Protected server logic verifies claims and does not trust `getSession()` as identity proof.
7. SSR refresh cookies and cache headers are preserved.
8. Intended destination is navigation context only.
9. Normal intended destination uses a dedicated short-lived HttpOnly cookie.
10. Cookie lifetime is 30 minutes.
11. Cookie uses `SameSite=Lax`.
12. `Secure` is enabled in production.
13. No explicit cookie Domain is set.
14. Initial allowed route family is `/dashboard` and `/dashboard/*`.
15. Stored intent is an internal relative pathname only.
16. Arbitrary query state is excluded until separately approved.
17. Absolute, external, malformed, stale, and unauthorized targets are rejected.
18. Secrets, credential artifacts, and mutation payloads are excluded.
19. Owner-state resolution takes precedence over intended navigation.
20. Intended navigation never grants authorization.
21. Consumed intent is single-use and cleared.
22. Google OAuth uses fixed `/auth/callback`.
23. Re-auth mutation payloads do not use the normal navigation cookie.
24. Recovery may preserve valid same-browser intent but safely falls back when unavailable.
25. Public routes remain anonymous.
26. `/ops/*` is excluded from normal Owner intended destinations.
27. Raw intended URLs are not general analytics/log payload.
28. Unsafe intended state never causes external redirect or authorization bypass.
