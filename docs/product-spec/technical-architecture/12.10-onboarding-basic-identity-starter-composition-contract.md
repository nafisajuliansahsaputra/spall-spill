# 12.10 — Onboarding Basic Identity Working & Starter Composition Contract

## Status

**LOCKED / CURRENT O01 S3-S4 IMPLEMENTATION AUTHORITY**

This contract resolves the implementation details required for:

- O01-S3 Basic Identity;
- onboarding Identity Working persistence;
- O01-S4 Starter Composition;
- Working revision boundaries;
- backward step navigation without progress regression.

It extends 12.9 without changing the locked six-step O01 product journey.

It does not yet define:

- modular Identity block persistence;
- Social / Contact / Generic Link editor persistence;
- first Product or Resource Draft persistence;
- public Identity projection;
- first-publication orchestration;
- onboarding completion.

---

## 1. Governing O01 Semantics

O01 remains one logical route:

`/onboarding`

Canonical semantic steps remain:

1. `claim_handle`
2. `primary_use_case`
3. `basic_identity`
4. `starter_composition`
5. `relevant_first_job`
6. `preview_publish`

S3 and S4 remain onboarding steps, not separate product destinations.

Completing S3 or S4 does not write:

`core.owners.onboarding_completed_at`

Only later successful first authoritative Identity publication completes onboarding.

---

## 2. Progress Frontier vs Navigation Cursor

`core.owner_onboarding_progress.current_step` is the authoritative onboarding progress frontier and default resume point.

It is not required to equal the earlier step the Owner is currently revisiting in the UI.

An Owner may navigate backward to an already available step without regressing `current_step`.

Technical navigation may use route-local state such as:

`/onboarding?step=claim_handle`

without creating another logical screen.

Rules:

- backward navigation does not mutate canonical progress by itself;
- a requested step later than the authoritative frontier is rejected or ignored;
- refreshing `/onboarding` without a technical step cursor resumes at the authoritative frontier;
- editing an earlier completed step must not silently delete or regress downstream Working state;
- successful earlier-step edits may change guidance but do not decrease the progress frontier.

This distinction preserves recoverable progress while allowing locked Back/edit-earlier behavior.

---

## 3. Basic Identity Minimum

The minimum valid onboarding Identity consists of:

- Handle — already authoritative through 12.9;
- Display Name — required.

Optional S3 fields:

- Profile Photo / Logo;
- Bio / Short Description.

Optional means genuinely optional.

An empty Profile Photo / Logo or Bio must not block:

- completion of S3;
- Preview;
- later Identity-only publication.

O01 S3 is not the full D02 Identity Editor.

---

## 4. Canonical Identity Working Boundary

Identity Working is application-owned canonical private state.

Conceptual relation:

`core.identity_working`

It is separate from:

- authentication identity;
- Handle namespace state;
- onboarding progress;
- Published/public Identity projection.

Minimum authoritative fields:

- `owner_id`
- `display_name`
- `bio`
- `profile_asset_key`
- `revision`
- `created_at`
- `updated_at`

One current Identity Working record exists at most once per Owner.

`owner_id` remains the stable canonical ownership identity.

Handle is not duplicated as Identity ownership identity.

---

## 5. Identity Working Creation Threshold

Merely:

- opening S3;
- focusing an input;
- typing client-local text;
- rendering a preview shell;

does not create canonical Identity Working state.

The first canonical Identity Working record is created only after the first successful authoritative S3 save containing a valid Display Name.

If the first persistence attempt fails:

- client-local input may remain visible;
- the UI must not claim Saved;
- no canonical Working record is assumed to exist.

Once successfully created, Identity Working remains durable across normal navigation, logout, refresh, and device/session changes.

---

## 6. Display Name Contract

Display Name is required for the first valid Identity Working save.

Display Name:

- is distinct from Handle;
- may contain Unicode human-readable text;
- is trimmed at its boundaries;
- must contain at least one non-whitespace character;
- is single-line;
- has a maximum canonical length of 80 Unicode code points for MVP;
- must not contain NUL or unsupported control characters.

Display Name does not need to be globally unique.

Changing Display Name does not change:

- `owner_id`;
- Handle namespace ownership;
- public route identity;
- authorization identity.

---

## 7. Bio Contract

Bio is optional plain textual content.

Canonical MVP behavior:

- surrounding whitespace is trimmed;
- an empty normalized Bio is stored as `NULL`;
- line breaks are allowed;
- maximum canonical length is 300 Unicode code points;
- arbitrary HTML, CSS, JavaScript, or executable markup semantics are not supported.

Bio validation failure is local to Bio and does not discard an already acknowledged valid Display Name or unrelated Working state.

---

## 8. Profile Photo / Logo Contract

Profile Photo / Logo is optional.

Canonical Identity Working reserves:

`profile_asset_key`

as a nullable platform-controlled asset reference.

Raw arbitrary public URLs are not canonical asset identity.

S3 remains valid when `profile_asset_key` is `NULL`.

The upload/storage transport, file validation, transformation, and deletion lifecycle are implemented in a dedicated Stage 6B storage subcheckpoint before the optional upload UI is considered complete.

Absence or temporary unavailability of the optional upload path must never make Display Name invalid.

---

## 9. Identity Working Revision

Every persisted Identity Working record has a monotonic revision.

The initial successfully persisted Identity Working revision is:

`1`

Subsequent authoritative Identity Working mutations require:

`base_revision = N`

and may commit only when:

`authoritative revision = N`

Successful mutation:

`revision = N + 1`

A stale mutation:

- returns a distinct `stale_write` result;
- changes no Identity Working fields;
- changes no Published state;
- does not automatically retry as last-write-wins.

When no Identity Working record exists yet, first creation uses an explicit creation boundary rather than pretending revision `0` is already persisted Working.

---

## 10. S3 Progress Advancement

The first successful valid Identity Working save while the progress frontier is:

`basic_identity`

atomically:

1. persists Identity Working;
2. advances onboarding frontier to:
   `starter_composition`;
3. increments onboarding progress revision.

If the frontier is already later than S3, editing Basic Identity:

- updates Identity Working revision;
- does not regress onboarding progress;
- does not destroy starter or later recoverable state;
- does not need to increment onboarding-progress revision unless that row itself changes.

A failed Identity Working save does not advance S3.

---

## 11. Working Persistence Truth

Canonical state meanings remain:

- Local / Unsaved;
- Saving;
- Saved / Working;
- Save Failed / Offline-Unconfirmed;
- Published / Live.

`Saved` means authoritative backend acknowledgement.

Client-only state, optimistic UI, debounce buffers, or queued requests are not Saved.

MVP does not promise offline-first editing.

Already acknowledged Identity Working survives normal interruption.

Unacknowledged local edits are not guaranteed across tab close, browser crash, device restart, storage clearing, or another device.

---

## 12. Identity Content vs Identity Layout

Identity content and Identity layout remain separate concepts.

Basic profile content must not be stored inside a reusable starter/template recipe.

Starter/layout state must not contain copied personal:

- Display Name;
- Bio;
- contact data;
- Social destination;
- owner media payload.

This preserves the locked rule:

`Identity Content ≠ Identity Layout`

---

## 13. Starter Composition Working Boundary

O01-S4 stores a small curated starting-layout choice.

Conceptual relation:

`core.identity_layout_working`

Minimum authoritative fields:

- `owner_id`
- `starter_key`
- `revision`
- `created_at`
- `updated_at`

One current Identity Layout Working record exists at most once per Owner.

The initial curated MVP starter keys are:

- `clean`
- `social_focus`
- `featured`
- `business`

These are layout/composition recipes, not account types.

They may be presented or ordered differently according to Primary Use Case, but all remain capability-neutral.

---

## 14. Starter Semantics

### `clean`

Neutral profile-first composition with minimal visual hierarchy.

### `social_focus`

Composition optimized for Identity plus Social/Link-oriented content.

### `featured`

Composition with stronger visual emphasis suitable for Creator or future Spill-oriented content.

It does not activate an empty Spill CTA.

### `business`

Composition oriented toward business identity, contact, and future resource-oriented content.

It does not create or require a Resource.

Starter keys describe initial layout emphasis only.

They do not:

- create permission boundaries;
- create persona-specific schemas;
- require Product or Resource;
- create public content by themselves;
- automatically publish;
- permanently lock later D02 layout choices.

---

## 15. Starter Selection and Primary Use Case

Primary Use Case may influence:

- recommended starter;
- starter ordering;
- explanatory guidance.

Primary Use Case does not remove starter options or enforce a starter.

`Other` remains compatible with every starter.

Changing Primary Use Case later does not silently change an already saved starter.

Changing starter later does not modify Primary Use Case.

---

## 16. Starter Creation Threshold

Merely entering S4 does not create Identity Layout Working.

The first layout Working record is created only after explicit Owner starter confirmation.

A failed first save creates no acknowledged layout Working record.

Once saved, the layout choice is recoverable account-side Working state.

---

## 17. Starter Layout Revision

Every persisted Identity Layout Working record has its own monotonic revision independent from Identity content revision.

Initial persisted layout revision:

`1`

Later authoritative starter changes require the last acknowledged layout base revision.

Stale layout writes:

- return `stale_write`;
- mutate no layout Working state;
- mutate no Identity content;
- mutate no Published state;
- do not silently retry.

---

## 18. S4 Progress Advancement

The first successful Starter save while the progress frontier is:

`starter_composition`

atomically:

1. persists Identity Layout Working;
2. advances onboarding frontier to:
   `relevant_first_job`;
3. increments onboarding progress revision.

If the frontier is already later than S4, changing Starter:

- updates only layout Working state and revision;
- does not regress onboarding frontier;
- does not delete downstream Product/Resource Draft or other recoverable state.

A failed Starter save does not advance S4.

---

## 19. Authenticated Read Boundary

The authenticated O01 state resolver may evolve to return the current Owner's:

- progress frontier;
- progress revision;
- Handle;
- Primary Use Case;
- Basic Identity Working state, if it exists;
- Identity Working revision, if it exists;
- Starter selection, if it exists;
- Layout Working revision, if it exists.

It accepts no target Owner ID.

It exposes no other Owner's private Working state.

---

## 20. Authenticated Mutation Boundaries

S3 and S4 mutation RPCs:

- require authenticated authority;
- derive canonical Owner from `auth.uid()`;
- accept no client-controlled target Owner ID;
- enforce account eligibility;
- enforce Working revision preconditions;
- enforce progress revision when advancing the frontier;
- update canonical private state transactionally;
- return acknowledged authoritative state.

Expected S3 semantic result classes include:

- `success`
- `invalid_display_name`
- `invalid_bio`
- `stale_write`
- `progress_stale`
- `owner_missing`
- `owner_not_eligible`

Expected S4 semantic result classes include:

- `success`
- `invalid_starter`
- `identity_required`
- `stale_write`
- `progress_stale`
- `owner_missing`
- `owner_not_eligible`

Internal failures remain generic application failures.

---

## 21. Private Schema / Authorization Boundary

Canonical Working tables remain private in `core`.

No direct `anon` or `authenticated` table privileges are granted.

Owner-facing access occurs through narrow authenticated RPCs in the dedicated API boundary.

SECURITY DEFINER functions:

- use a fixed empty search path;
- resolve identity from authenticated context;
- do not trust client Owner identity;
- receive explicit EXECUTE grants only where required.

Authentication remains separate from authorization.

---

## 22. Published Isolation

Stage 6B does not create public Identity projection.

Identity Working save does not:

- publish;
- update a public route projection;
- create Platform Activation;
- complete onboarding.

Starter save does not:

- publish;
- create public blocks;
- activate Spill;
- complete onboarding.

Working and Published remain isolated.

`6B.2 — S3 application UI + backward technical navigation`
