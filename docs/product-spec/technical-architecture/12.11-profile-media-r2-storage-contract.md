# 12.11 — Profile Media / Logo R2 Storage Contract

## Status

**LOCKED / CURRENT PROFILE-MEDIA STORAGE IMPLEMENTATION AUTHORITY**

This contract resolves the Stage 6B.3 implementation boundary for optional
O01-S3 Profile Photo / Logo media.

It extends:

- 12.4 Production Technology Stack & Security Architecture;
- 12.10 Onboarding Basic Identity Working & Starter Composition Contract.

It does not change the locked O01 six-step journey.

It does not define the later public-media publication projection.

---

## 1. Purpose

Allow an authenticated Owner to optionally upload a Profile Photo / Logo while
preserving:

- Working-versus-Published isolation;
- authoritative Owner scope;
- safe user-generated media processing;
- immutable canonical media;
- storage/database separation;
- recoverable failure behavior;
- optional onboarding semantics.

Profile media remains optional.

Failure to upload media must never make a valid Display Name invalid.

---

## 2. Storage / Database Separation

Binary image bytes are not stored in PostgreSQL.

Cloudflare R2 stores object bytes.

PostgreSQL stores:

- upload intent metadata;
- canonical media ownership;
- stable media reference;
- canonical object metadata;
- the selected `profile_asset_key` on Identity Working.

`core.identity_working.profile_asset_key` is a platform-controlled stable asset
reference.

It is not:

- image bytes;
- Base64 image data;
- a client-controlled arbitrary URL;
- a presigned URL;
- a temporary staging object key.

Presigned URLs are transport credentials only and are never canonical database
state.

---

## 3. Working Media Is Not Public Media

Stage 6B.3 Profile Media belongs to private Owner Working state.

Uploading or selecting Profile Media does not:

- publish the media;
- make the Identity public;
- update the Published Identity projection;
- complete onboarding;
- create Platform Activation.

The working-media bucket remains private.

Later first Publish / recurring Publish mechanics determine how an acknowledged
Working asset becomes safely available in the public projection.

Public-media delivery is intentionally deferred.

---

## 4. Cloudflare R2 Authority

Profile-media object storage uses Cloudflare R2 through its S3-compatible API.

Application server credentials use a bucket-scoped R2 token with:

`Object Read & Write`

permission only for the dedicated profile-media bucket.

Do not use:

- account-wide Admin Read & Write;
- Cloudflare global API credentials;
- unrelated bucket credentials.

Canonical server environment:

- `R2_S3_ENDPOINT`
- `R2_ACCESS_KEY_ID`
- `R2_SECRET_ACCESS_KEY`
- `R2_PROFILE_BUCKET`

These values are server-only.

None use the `NEXT_PUBLIC_` prefix.

`R2_S3_ENDPOINT` is explicit rather than assuming one hardcoded hostname so the
implementation remains compatible with the bucket's Cloudflare R2 endpoint /
jurisdiction.

---

## 5. Supported Input Media

MVP accepted source formats:

- JPEG;
- PNG;
- WebP.

Canonical accepted source MIME values:

- `image/jpeg`
- `image/png`
- `image/webp`

Unsupported formats are rejected.

MVP intentionally does not accept:

- SVG;
- GIF;
- HEIC / HEIF;
- AVIF input;
- PDF;
- arbitrary binary upload;
- video.

SVG is excluded because owner-supplied SVG can contain active or unexpectedly
complex document semantics and is unnecessary for MVP Profile Photo / Logo.

---

## 6. Source File Limits

Maximum source upload size:

`5 MiB`

or:

`5,242,880 bytes`

Client-side file size and MIME checks are UX convenience only.

They are not authoritative security controls.

The authoritative server finalization path verifies the object actually stored
in R2 before accepting it as canonical media.

A file larger than the application limit is rejected even if R2 itself is
capable of storing a larger object.

---

## 7. Image Decode / Pixel Limits

An accepted source must decode as a real supported image.

MVP maximum decoded image dimensions:

`4096 × 4096`

MVP maximum decoded pixel count:

`16,777,216`

Images exceeding the safe decoded-pixel boundary are rejected.

This protects the application from oversized or decompression-heavy image
payloads even when the compressed source file is below the byte-size limit.

Animated / multi-page image content is not supported.

If a source container reports multiple frames/pages, the upload is rejected
rather than silently choosing one frame.

---

## 8. Upload Intent

Direct browser upload never receives permanent R2 credentials.

Before an upload, the application creates a short-lived authoritative upload
intent.

Conceptual private relation:

`core.profile_media_upload_intents`

Minimum fields:

- `id`
- `owner_id`
- `expected_content_type`
- `declared_byte_size`
- `staging_object_key`
- `status`
- `expires_at`
- `created_at`
- `consumed_at`

Canonical statuses include:

- `pending`
- `processing`
- `consumed`
- `rejected`
- `expired`

The upload intent belongs to exactly one canonical Owner.

The browser never chooses another Owner.

---

## 9. Upload Intent Eligibility

A Profile Media upload intent may be created only when:

- there is a valid authenticated Supabase principal;
- the principal resolves to one canonical Owner;
- Owner account state is eligible;
- onboarding remains incomplete for O01 usage;
- the Owner has reached at least O01-S3 Basic Identity.

S1/S2 cannot be bypassed by uploading media.

A completed Owner will later use the recurring D02 media workflow rather than
replaying O01.

---

## 10. Server-Only Media Orchestration Authority

Media orchestration requires limited elevated database operations that must not
be callable by ordinary browser clients.

Hosted production uses a Supabase server-only Secret key:

`SUPABASE_SECRET_KEY`

using the current `sb_secret_...` key model.

A local Supabase development stack may temporarily use its generated legacy
service-role credential when the local stack does not provide an equivalent
new Secret key:

`SUPABASE_SERVICE_ROLE_KEY`

The production implementation prefers `SUPABASE_SECRET_KEY`.

Both are backend-only elevated credentials.

Neither may:

- use `NEXT_PUBLIC_`;
- be serialized to React;
- be returned from a Route Handler / Server Action;
- be logged;
- be included in browser bundles;
- be written to source control.

The elevated client is isolated in a server-only module.

It is not reused as the normal application client.

Normal authentication is still resolved first using the request-scoped
user-session client.

Elevated database access begins only after the server has independently
verified the current authenticated principal.

---

## 11. Service-Only Database Functions

Media orchestration may use narrow service-only functions inside the Data API
boundary.

Conceptual functions include:

`api.create_profile_media_upload_intent_server(...)`

`api.resolve_profile_media_upload_intent_server(...)`

`api.complete_profile_media_upload_server(...)`

These functions:

- may accept the already verified Auth user ID from trusted server code;
- resolve the canonical Owner internally;
- do not trust a browser-provided Owner ID;
- are `SECURITY DEFINER`;
- use an empty fixed `search_path`;
- grant EXECUTE only to the elevated server role;
- grant no EXECUTE to `anon` or `authenticated`.

The elevated server role receives `USAGE` on the dedicated `api` schema only
as required to reach those explicitly granted RPCs.

That schema-level `USAGE` does not grant:

- direct `core` schema access;
- direct private-table privileges;
- implicit EXECUTE on other revoked functions.

Browser clients cannot directly create, inspect, or complete internal media
records through these service-only functions.

---

## 12. Staging Object Namespace

Browser uploads go only to temporary staging objects.

Canonical staging namespace:

`staging/profile/<upload-id>/<random-token>`

The key is generated by trusted server code.

The browser cannot choose an arbitrary bucket object path.

Staging keys contain no required human-readable Handle.

Handle mutation therefore does not rename media objects.

Staging objects are never referenced by Identity Working.

---

## 13. Presigned PUT

The server creates a presigned R2 `PutObject` URL only for the exact staging
object.

Canonical expiration:

`300 seconds`

or:

`5 minutes`

The signature binds the expected source `Content-Type`.

The browser must upload using the signed `Content-Type`.

The presigned URL is treated as a bearer credential.

It is:

- short lived;
- specific to one staging object;
- specific to one PUT operation;
- never persisted as application state;
- never logged deliberately.

A presigned URL may technically remain reusable until expiry, therefore
canonical Profile Media never points directly at the staging object.

---

## 14. Browser CORS Boundary

Browser-to-R2 upload requires an explicit R2 CORS policy.

Allowed origins are explicit application origins.

No wildcard production origin is used.

Development may include:

`http://localhost:3000`

Production origin is configured explicitly once the production application
origin is final.

Required methods for the working-media browser path may include:

- `PUT`
- `GET`
- `HEAD`

Allowed request headers include only those actually required, including:

- `Content-Type`

`ETag` may be exposed to the browser where useful.

CORS does not replace authentication, Owner authorization, or presigned URL
scope.

---

## 15. Upload Initiation Rate Boundary

Issuing upload intents and presigned URLs is an abuse-sensitive action.

The application applies action-specific rate limiting before public launch.

Rate limiting is scoped at minimum by authenticated principal and may also use
request/network signals according to the platform abuse-prevention contract.

Rate-limit failure creates no canonical media asset.

Distributed production enforcement follows the locked Upstash rate-limiting
architecture.

---

## 16. Finalization Is Required

A successful R2 PUT does not mean the Profile Media is accepted.

After browser upload, the application performs a server-side finalization step.

Until finalization succeeds:

- the staging file is untrusted;
- no canonical asset exists;
- Identity Working does not reference it;
- UI must not label it Saved Profile Media.

---

## 17. Finalization Object Verification

Finalization verifies the current authenticated principal again.

The server then resolves the upload intent and verifies:

- intent belongs to the same canonical Owner;
- intent is still valid;
- intent is not already consumed;
- staging key matches the authoritative intent;
- declared MIME is supported.

The server performs R2 object inspection.

At minimum it checks:

- object exists;
- authoritative object byte size;
- stored Content-Type;
- byte size does not exceed 5 MiB.

The client-declared file size is not authoritative.

---

## 18. Full Image Decode / Sanitization

Metadata and MIME labels alone are insufficient.

The server downloads the untrusted staging object and decodes it using a
server-side image processing library.

Canonical Stage 6B.3 processor:

`sharp`

The processor verifies that the actual decoded format is one of:

- JPEG;
- PNG;
- WebP.

MIME / decoded-format mismatch is rejected.

Malformed images are rejected.

Unsupported multi-frame / animated content is rejected.

---

## 19. Canonical Transformation

Untrusted source bytes never become the canonical Working media object
unchanged.

After successful decode, the server creates a sanitized canonical rendition.

Canonical MVP processing:

1. honor source orientation;
2. strip EXIF and nonessential source metadata;
3. preserve image aspect ratio;
4. constrain result inside `2048 × 2048`;
5. never upscale a smaller source merely to meet that limit;
6. encode canonical output as static WebP;
7. preserve transparency where supported;
8. use platform-controlled encoding settings.

Initial WebP quality target:

`85`

The exact implementation may tune encoder internals later without changing the
semantic media contract.

Canonical stored MIME:

`image/webp`

---

## 20. Immutable Canonical Media

A successfully processed Profile Media asset receives a new immutable asset
identity.

Conceptual private relation:

`core.profile_media_assets`

Minimum fields:

- `asset_key`
- `owner_id`
- `object_key`
- `stored_content_type`
- `byte_size`
- `width`
- `height`
- `source_upload_intent_id`
- `created_at`

`asset_key` is the stable application reference stored by Identity Working.

`object_key` is the private R2 storage path.

They are separate so storage layout can evolve without requiring Identity
records to store public URLs.

Canonical object namespace:

`working/profile/<asset-key>.webp`

A canonical object is never overwritten in place.

Replacing a Profile Photo / Logo creates a new asset.

This provides immutable version identity for Working / Published isolation.

---

## 21. Asset Registration Order

Safe canonicalization order is:

1. validate authenticated Owner and upload intent;
2. inspect staging object;
3. decode source;
4. create sanitized WebP bytes;
5. upload immutable canonical object to R2;
6. register canonical asset metadata authoritatively;
7. mark upload intent consumed;
8. make the new `asset_key` available to the S3 form;
9. delete staging object on a best-effort basis.

If canonical R2 upload succeeds but database registration fails:

- Identity Working remains unchanged;
- the canonical object is an unattached orphan;
- it may be removed later by safe garbage collection.

The product must not claim the asset is attached.

---

## 22. Staging Cleanup

Staging cleanup is defense in depth.

After successful finalization, the application attempts to delete the staging
object.

Deletion failure does not roll back an already valid canonical asset.

The R2 bucket also uses a lifecycle rule for the staging prefix so abandoned
or re-uploaded staging objects do not remain indefinitely.

Initial staging retention target:

`1 day`

Staging lifecycle cleanup may delete only the staging namespace.

It must never apply broadly to canonical media objects.

---

## 23. S3 Form Integration

Finalized media is not automatically attached to Identity Working.

Finalization returns an acknowledged platform `asset_key` to the S3 editing
context.

The current S3 form then treats that asset selection as local intended Working
state until the Basic Identity save succeeds.

`api.save_current_owner_basic_identity(...)` evolves to accept the intended
Profile Media asset reference.

When a non-null `profile_asset_key` is submitted, the backend verifies:

- asset exists;
- asset belongs to the current canonical Owner;
- asset is a canonical ready Profile Media asset.

A client cannot attach another Owner's asset.

---

## 24. First S3 Save With Media

Identity Working creation threshold remains unchanged:

a canonical Identity Working record is first created only after successful
authoritative S3 save with a valid Display Name.

Media may already have been uploaded and canonicalized before that save.

This does not mean Identity Working already exists.

Before S3 save:

- the asset may be a valid private unattached Owner media asset;
- the form selection is not yet part of Saved Identity Working.

Successful first S3 save atomically stores:

- Display Name;
- optional Bio;
- optional `profile_asset_key`;

and advances S3 to S4 according to 12.10.

---

## 25. Existing Identity Media Change

For an existing Identity Working revision, changing media follows the same
Identity revision precondition as other Basic Identity fields.

Conceptually:

`save(baseIdentityRevision = N)`

may change:

- Display Name;
- Bio;
- Profile Media selection;

only when authoritative Identity Working revision is still `N`.

Success commits:

`revision = N + 1`

when acknowledged Working state actually changes.

Stale writes do not change the selected media.

---

## 26. Removing Profile Media

Removing Profile Photo / Logo means setting the intended Working
`profile_asset_key` to `NULL`.

Removal:

- requires the current acknowledged Identity Working revision;
- increments Identity revision when it changes Working state;
- does not immediately delete the underlying immutable asset;
- does not alter the Handle;
- does not alter Primary Use Case;
- does not automatically publish.

---

## 27. Do Not Delete Previous Canonical Asset On Working Save

A prior canonical media asset must not be deleted merely because a newer
Identity Working revision selects another asset.

Future Published Identity may still reference the older asset.

This is required by:

`Working ≠ Published`

Therefore replacement flow is:

`old asset remains immutable`

plus:

`new Working revision references new asset`

until later lifecycle logic proves the old asset is unreferenced.

---

## 28. Canonical Asset Garbage Collection

Canonical Profile Media deletion is reference-safe.

A canonical asset may be garbage-collected only when the system can prove that
it is no longer referenced by any authoritative state that requires it.

The reference scan must eventually include at least:

- current Identity Working;
- Published Identity projection;
- any publication/recovery state that intentionally retains that revision.

Stage 6B.3 does not yet have enough Published-state information to safely delete
replaced canonical assets.

Therefore automatic canonical-asset deletion is deferred until the publication
model exists.

Unattached assets may later use a conservative retention policy once the full
reference graph is available.

---

## 29. Working Preview

Existing acknowledged Working Profile Media may be previewed by the
authenticated Owner.

The database still stores only `asset_key`.

The server resolves that key to the private R2 object and may issue a short
lived read URL or equivalent authenticated delivery mechanism.

Preview transport URLs are ephemeral.

They are never written back into Identity Working.

Owner Preview remains separate from public delivery.

---

## 30. Failure Truth

The UI distinguishes:

- selected locally;
- uploading;
- processing;
- upload failed;
- ready but not yet attached;
- Saved / Working.

A successful browser PUT is not labelled Saved.

A successful image processing step is not by itself an Identity Working save.

Only an acknowledged Basic Identity mutation makes the selected asset part of
Saved Identity Working.

Failure at any stage must not silently replace the last acknowledged
`profile_asset_key`.

---

## 31. Retry / Idempotency

Upload intent finalization is duplicate-safe.

Once an intent is consumed, retrying the same finalization must not create
multiple canonical assets.

A repeated request may return the already completed result where the server can
prove the same authoritative intent was completed.

It must not create another asset solely because a network response was lost.

---

## 32. Secret Isolation

R2 credentials and Supabase elevated server credentials remain server-only.

Do not expose:

- `R2_SECRET_ACCESS_KEY`;
- `SUPABASE_SECRET_KEY`;
- local `SUPABASE_SERVICE_ROLE_KEY`;

to:

- browser code;
- client components;
- public environment variables;
- analytics;
- error messages;
- repository content.

`.env.example` contains placeholders only.

Real secrets remain ignored/local or configured in the deployment secret
environment.

---

## 33. R2 Token Scope

The R2 application token uses the smallest practical scope:

`Object Read & Write`

restricted to:

`R2_PROFILE_BUCKET`

The application does not require bucket-management Admin permission for normal
runtime Profile Media operations.

Bucket creation and CORS/lifecycle configuration are infrastructure setup
operations and are not performed with normal runtime credentials.

---

## 34. Logging / Privacy

Application logs may record operational identifiers such as:

- upload intent ID;
- opaque asset key;
- processing status;
- byte size;
- dimensions;
- error class.

Logs must not unnecessarily contain:

- presigned URLs;
- R2 secret credentials;
- Supabase Secret key;
- raw image bytes;
- Bio;
- private object response bodies.

Media upload analytics record workflow events, not image content.

---

## 35. Testing Requirements

Stage 6B.3 tests must prove at least:

### Database / authorization

- upload intent belongs to one canonical Owner;
- browser roles cannot access private media tables directly;
- browser roles cannot execute service-only media functions;
- server-only functions use fixed empty `search_path`;
- S1/S2 cannot be bypassed with media upload;
- media save cannot attach another Owner's asset;
- invalid/nonexistent asset reference is rejected;
- first S3 save may include a valid optional Profile Media asset;
- S3 remains valid with no Profile Media;
- media replacement increments Identity Working revision;
- stale Identity mutation cannot replace media;
- removing media stores `NULL`;
- media changes do not complete onboarding;
- media changes do not mutate Handle or Primary Use Case.

### Application / storage

- only JPEG/PNG/WebP source MIME is accepted;
- source over 5 MiB is rejected;
- malformed image is rejected;
- MIME/decoded-format mismatch is rejected;
- animated/multi-page source is rejected;
- decoded pixel limit is enforced;
- EXIF orientation is normalized;
- canonical result is static WebP;
- metadata is stripped;
- canonical dimensions remain within 2048 × 2048;
- canonical object key is server-generated;
- staging key is never stored as Identity Working media;
- duplicate finalize is idempotent;
- expired intent cannot finalize normally;
- old Working media is retained when replaced;
- failure before authoritative S3 save leaves prior Working unchanged.

## 37. Infrastructure Setup Boundary

Before live R2 runtime testing, infrastructure setup must create:

1. dedicated Profile Media R2 bucket;
2. bucket-scoped Object Read & Write runtime token;
3. explicit browser CORS policy;
4. staging-prefix lifecycle cleanup;
5. deployment secret variables.

Bucket setup is performed once through Cloudflare infrastructure controls.

Normal runtime code does not require Cloudflare account-admin permission.
