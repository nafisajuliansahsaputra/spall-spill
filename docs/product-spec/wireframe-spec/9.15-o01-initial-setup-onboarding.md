# 9.15 — O01 Initial Setup / Onboarding Screen-Level UX Specification — LOCKED

## 1. Screen Identity

- **ID:** O01
- **Name:** Initial Setup / Onboarding
- **Zone:** Authentication / Onboarding
- **Route:** `/onboarding`
- **Shell:** Focused Authentication / Onboarding Shell
- **Primary data context:** authenticated owner with incomplete onboarding, account-side onboarding progress, Handle availability/namespace state, Primary Use Case personalization metadata, onboarding Identity Working state, optional first Product/Resource Draft, preview bundle state, first-publish orchestration state, and activation outcomes after authoritative publication

O01 is one logical recoverable onboarding flow with six semantic steps:

```text
O01-S1 Claim Handle
O01-S2 Primary Use Case
O01-S3 Basic Identity
O01-S4 Starter Composition
O01-S5 Relevant First Job
O01-S6 Preview & Publish
```

> **Progressive onboarding, universal account.**
>
> **Guidance adapts; capabilities do not disappear.**

---

## 2. Purpose

Move an authenticated new owner from an account-only state to the first valid public Spall Spill presence with the minimum required setup, while preserving optionality, recoverability, explicit publication, and the universal capability model.

O01 is not a comprehensive product tutorial or full configuration wizard.

---

## 3. Primary User Job

> **Reach a valid first public presence with minimum required effort, review what will become public, and explicitly publish when ready.**

Canonical semantic flow:

```text
Claim Handle
→ select Primary Use Case
→ complete minimum Identity
→ accept/select a starter composition
→ optionally complete the most relevant first job
→ Preview intended public state
→ explicit first Publish
→ authoritative publication
→ onboarding complete
→ D01 universal Owner Workspace
```

---

## 4. User Context

Primary viewer:

- authenticated owner whose onboarding is incomplete.

Relevant contexts include:

- genuine new account arriving from A01;
- returning owner from A02 after leaving onboarding earlier;
- recovered owner from A03 whose onboarding remains incomplete;
- owner resuming from another browser/device;
- owner whose session expired while completing onboarding;
- owner who changes an earlier onboarding decision after starting later work;
- owner whose optional first Product/Resource is valid, incomplete, invalid, or intentionally skipped;
- owner whose first Publish succeeds or fails.

O01 never changes capability permissions based on Primary Use Case.

---

## 5. Entry Paths

Meaningful entries include:

- A01 new-account success through the owner-state resolver;
- A02 Login for an onboarding-incomplete account;
- A03 Recovery for an onboarding-incomplete recovered account;
- direct `/onboarding` access by an authenticated incomplete owner;
- re-entry after normal interruption/logout/session expiry;
- retry after first-publish failure.

If an authenticated active owner has already completed onboarding, `/onboarding` must not replay account onboarding as a normal recurring workflow.

---

## 6. Exit Paths

Major exits include:

- D01 after successful first authoritative Identity publication and onboarding completion;
- A02 if authentication is required again after session expiry;
- A03 if account access must be recovered rather than normally re-authenticated;
- safe logout/leave/return-later behavior while onboarding remains incomplete;
- no direct bypass to normal Owner Workspace while required onboarding remains incomplete.

Optional Product/Resource work may be skipped without blocking valid Identity publication.

---

## 7. Information Hierarchy

Canonical semantic priority:

1. **Current onboarding step + meaningful progress context**.
2. **Minimum task required for the current step**.
3. **Primary Continue / Publish action**.
4. **Back / Skip where semantically allowed**.
5. **Local validation and recoverable-state feedback**.
6. **Intent-adaptive guidance** without permission gating.
7. **Preview and first-publication truth** at S6.

The six-step architecture remains stable even when S5 guidance differs by Primary Use Case.

---

## 8. Section / Region Structure

### O01-S1 — Claim Handle

Handle establishes the public namespace and is distinct from Display Name.

Requirements:

- validate format, availability, and reserved system namespaces;
- Handle selection happens before Basic Identity;
- invalid/unavailable Handle creates local actionable feedback;
- Handle failure never discards unrelated valid onboarding work;
- suggestions may be offered but are not required;
- Handle is not chosen automatically without owner confirmation.

### O01-S2 — Primary Use Case

Required choices include:

- Creator;
- Affiliate / Product Recommendations;
- Business / UMKM;
- Personal Link-in-Bio;
- Other.

Rules:

- this is personalization metadata, not account type or authorization;
- all owners retain the same capability system;
- guidance, starter emphasis, first-job suggestion, and later workspace emphasis may adapt;
- owner can change Primary Use Case later without migration or content loss;
- `Other` remains a neutral escape hatch.

### O01-S3 — Basic Identity

Minimum onboarding Identity after Handle:

- **Display Name — required**;
- profile photo/logo — optional;
- Bio — optional.

O01 does not require the full D02 editor, full social/contact setup, advanced Appearance, or arbitrary block composition here.

Optional fields remain truly optional and never become hidden publish blockers solely because they are empty.

### O01-S4 — Starter Composition

Starter selection is a fast starting-point decision, not a full design-editor step.

Intent-relevant examples may emphasize:

```text
Personal → profile + Social/Links
Affiliate → Identity with Spill-ready placement
Business → brand/contact/resource-oriented composition
Creator → profile/social/featured-oriented composition
Other → neutral clean starting point
```

Rules:

- small/curated starter set rather than marketplace-scale browsing;
- selection remains reversible/editable later in D02;
- starter never changes capability permission;
- advanced typography/theme/layout refinement is deferred;
- applying a starter must not create permanent role or layout lock.

### O01-S5 — Relevant First Job

Guidance adapts while capabilities remain universal.

Canonical emphasis:

```text
Personal → Social / useful Link connection
Creator → personal-brand / Social connection; Spill optional
Affiliate → First Product strongly encouraged
Business / UMKM → First Resource strongly encouraged
Other → neutral Identity-first guidance
```

Rules:

- Product/Resource are skippable for every use case;
- Skip must be a genuine accessible path, not a hidden pseudo-option;
- Affiliate First Product reuses D04 paste-first/manual-fallback semantics where useful but stays logically inside O01;
- Business First Resource reuses D06 meaning-first/source/title semantics where useful but stays logically inside O01;
- Category/taxonomy never blocks first activation;
- persistent Product/Resource reference remains system-managed;
- meaningful first Product/Resource work is recoverable Draft/Working state;
- changing Primary Use Case or earlier steps never silently destroys later recoverable Item work;
- changing guidance does not migrate or delete capability data.

### O01-S6 — Preview & Publish

S6 is the mandatory first-publication review state.

Preview uses the current onboarding Working state and must show the intended public result closely enough for owner review.

Possible preview bundles:

```text
Identity only
Identity + valid Product
Identity + valid Resource
```

A Spill/Resource CTA may participate in the first public Identity only when:

- it is visible in Preview; and
- the referenced Spill content is valid for publication in the same first-publish bundle.

No empty public Spill or dead Spill CTA is allowed.

### Invalid Optional Item Resolution

If Identity is valid but an optional Product/Resource is invalid at S6, the system requires an explicit resolution:

```text
Fix Item
OR
Publish Identity Only
```

Rules:

- invalid Item is never silently published;
- invalid Item is never silently deleted/discarded;
- Publish Identity Only retains the Item as recoverable Draft/unpublished work;
- activation reflects the authoritative public outcome only.

### First Publish

When Identity plus a valid first Product/Resource are prepared, O01 supports **one final user-level Publish intent** for the valid onboarding bundle.

The owner is not forced through separate Identity/Product/Spill publication ceremonies.

First Publish must:

- be explicit;
- validate the intended bundle;
- behave atomically/coherently from the public/user perspective;
- claim success only after authoritative persistence;
- prevent duplicate submission;
- preserve Working/Draft state on failure.

### Onboarding Completion

**Successful first authoritative Identity publication completes onboarding.**

This is true whether the outcome is:

- Identity only;
- Identity + Product;
- Identity + Resource.

Registration, finishing steps, reaching Preview, or a failed Publish do not complete onboarding.

After completion, the owner enters the universal D01 Owner Workspace rather than a persona-specific dashboard or permanent success page.

### Account-Side Progress Persistence

Reasonably recoverable onboarding state is account-side resumable.

It may include:

- current semantic step;
- Handle progress;
- Primary Use Case;
- Basic Identity state;
- starter selection;
- first Product/Resource Draft where applicable;
- unresolved validation state where safe;
- intended preview/publish bundle context.

Normal interruption must not intentionally force restart from S1.

### Step Navigation and Earlier-Decision Changes

Owner may navigate back between completed/available steps.

Changing an earlier value:

- may adapt guidance;
- may change validation requirements of the intended bundle;
- must not silently destroy unrelated valid work.

Example:

```text
Affiliate → starts Product
→ back to S2 → changes to Creator
→ Product Draft retained
→ guidance changes
```

## 9. Actions

### Primary actions

State-dependent:

- claim/confirm Handle;
- select Primary Use Case;
- continue after minimum Basic Identity;
- accept/select Starter;
- complete or skip Relevant First Job;
- Preview;
- Publish the valid onboarding bundle;
- retry failed Publish.

### Secondary actions

- Back to previous onboarding step;
- Skip optional Product/Resource first job;
- edit/fix invalid optional Item;
- choose Publish Identity Only when explicitly offered;
- safely leave/logout and resume later.

### Sensitive / publication actions

First Publish is the key public-state-changing action and requires authoritative validation/persistence.

---

## 10. Entity / Data Context

O01 may operate on:

- authenticated owner account;
- onboarding-complete state;
- Handle namespace claim;
- Primary Use Case personalization metadata;
- onboarding Identity Working state;
- starter-composition selection;
- optional first Product/Resource Draft;
- system-managed Spill Reference where allocated;
- first-publish bundle;
- activation outcomes derived after authoritative publication.

O01 does not create persona-specific account permissions.

---

## 11. Critical States

- Fresh onboarding / S1 ready.
- Handle validating / available / unavailable / invalid / reserved.
- Primary Use Case selected.
- Basic Identity incomplete / valid minimum.
- Starter loading / selected / unavailable fallback.
- Relevant First Job default / in progress / skipped.
- First Product extraction success / partial / failure / manual fallback where applicable.
- First Resource valid / invalid / incomplete where applicable.
- Resumed onboarding after interruption.
- Session expired / re-auth required.
- Preview ready.
- Identity valid + optional Item valid.
- Identity valid + optional Item invalid.
- Fix Item selected.
- Publish Identity Only selected.
- Publishing / duplicate-submit protected.
- Publish failure with work retained.
- Authoritative Publish success.
- Platform Activation only.
- Platform + Spill Activation.
- Platform + Spill + Commerce Activation.

These remain O01 states rather than additional logical screens.

## 12. Responsive Specification

### Mobile — First-class

Canonical structure:

```text
semantic progress
→ current focused task
→ primary Continue / Publish
→ Back / Skip where applicable
→ local validation/help
```

Requirements:

- full onboarding can be completed on mobile;
- S5 Product paste works naturally from mobile marketplace-copy workflows;
- optional metadata does not bury the required path;
- Preview remains usable on mobile;
- keyboard/input does not hide critical action/feedback;
- no desktop-only continuation requirement.

### Desktop — First-class

Desktop may add supporting context, side preview, or richer starter comparison without increasing required work.

The same six semantic steps, validation, optionality, and completion rules apply.

### Adaptation Rules

- breakpoint changes do not create separate onboarding documents/screens;
- semantic progress remains recognizable;
- capability availability never changes by viewport;
- accessible focus/reading order remains coherent.

---

## 13. Navigation / Context Preservation

- `/onboarding` remains the one canonical O01 route family;
- technical step/query state may vary without adding product screen IDs;
- account-side progress survives normal leave/logout/session interruption;
- A02/A03 return onboarding-incomplete owners to the appropriate resumable O01 state;
- owner may move backward without silent data loss;
- no `Skip entire onboarding → normal Dashboard` bypass exists;
- successful first authoritative Identity publication transitions to D01;
- recurring Identity/Product/Resource work after completion belongs to D02/D04/D06/D03 rather than replaying O01.

---

## 14. Interaction & Feedback Rules

- onboarding asks only enough to reach a valid first experience;
- Handle and Display Name remain distinct;
- Primary Use Case changes guidance, not permission;
- optional means genuinely optional;
- starter selection is quick and reversible later;
- Product/Resource first jobs remain skippable;
- first Product/Resource work is recoverable;
- errors are local to affected Handle/link/Item where possible;
- changing earlier steps never silently deletes later recoverable work;
- Preview precedes first public Publish;
- invalid optional Item requires explicit Fix vs Publish Identity Only;
- no empty public Spill or dead Spill CTA;
- publication success is authoritative, not optimistic fiction;
- first authoritative Identity publication completes onboarding;
- completion enters the universal adaptive Owner Workspace;
- onboarding choices remain editable later and never become role locks.

---

## 15. Accessibility Responsibilities

O01 must support:

- semantic step/progress announcement;
- labelled inputs and clear required-vs-optional distinctions;
- Handle availability/errors associated with the Handle control;
- keyboard/focus access through all steps;
- starter choices with accessible names/state;
- accessible Skip and Back actions;
- Product/Resource embedded controls that preserve D04/D06 accessibility expectations where reused;
- validation summaries/local errors that identify the affected field/Item;
- Preview with meaningful reading order;
- Publish pending/failure/success announcements;
- no status conveyed by color alone;
- touch-safe mobile interactions.

- Preview reached;

- Publish Identity Only chosen;

## Locked 9.15 Decisions

1. O01 is one six-step recoverable onboarding flow.
2. Progressive onboarding overrides comprehensive setup pressure.
3. Handle is claimed before Basic Identity and remains distinct from Display Name.
4. Primary Use Case is required personalization metadata, never capability authorization.
5. Minimum Basic Identity after Handle is Display Name; photo/logo and Bio remain optional.
6. Starter selection is fast, intent-relevant, reversible, and not advanced design configuration.
7. S5 guidance adapts by intent while capability access remains universal.
8. Product/Resource first jobs are genuinely skippable.
9. Onboarding Product/Resource branches remain logically inside O01 while reusing D04/D06 semantics where useful.
10. Category does not block first activation and Item references remain system-managed.
11. Meaningful first Item work and overall onboarding progress are recoverable/account-side resumable.
12. Earlier-step changes never silently destroy later recoverable work.
13. S6 Preview is required before first public Publish.
14. First-publish Spill CTA requires preview visibility plus valid publishable Spill content.
15. Valid Identity + valid optional Item supports one final user-level Publish intent.
16. Invalid optional Item requires explicit Fix Item or Publish Identity Only.
17. Publish Identity Only retains the invalid Item as Draft and reflects actual activation truth.
18. Identity-only outcome exposes no empty Spill/dead Spill CTA.
19. First Publish is explicit, coherent/atomic from the public perspective, duplicate-submit safe, and authoritative.
20. Publish failure preserves work and keeps onboarding incomplete.
21. Successful first authoritative Identity publication completes onboarding.
22. Completion enters D01 universal Owner Workspace, not a persona-specific/permanent success screen.
23. Registration, step completion, Preview, and failed Publish are not Activation.
24. Mobile and desktop share the same six semantic steps and are both first-class.
25. No whole-onboarding bypass to the normal Dashboard exists while onboarding remains incomplete.
