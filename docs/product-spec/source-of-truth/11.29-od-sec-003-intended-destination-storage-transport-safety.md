# 11.29 — OD-SEC-003 Intended-Destination Storage / Transport / Safety — LOCKED

## Decision identity

- Decision ID: **OD-SEC-003**
- Stage: Stage 11 JIT resolution during Stage 12 implementation
- Priority: P0
- Status: **LOCKED**
- Affected: A01 Sign Up, A02 Login/re-authentication, A03 Recovery, protected Owner-route interception, post-auth owner-state resolver

> Preserve navigation intent without turning navigation state into an open redirect, authorization bypass, replayable mutation, or sensitive URL payload.

## Canonical rule

The post-auth intended destination is **navigation intent only**.

It never carries mutation authority and never bypasses the owner-state resolver.

Canonical order after successful authentication/recovery is:

```text
authentication succeeds
→ resolve canonical Spall Spill Owner
→ resolve current account lifecycle/onboarding state
→ Suspended/restricted => D10
→ Onboarding incomplete => O01
→ Active + complete
   → consume and validate intended Owner destination, if any
   → authorize current actor for that destination
   → restore destination when still valid
   → otherwise D01
```

## Storage and transport

Normal pre-auth intended Owner navigation is stored as a **short-lived server-issued HttpOnly cookie token**, not as authoritative browser storage and not as a raw external URL.

Baseline properties:

- HttpOnly;
- Secure in production;
- SameSite=Lax so normal top-level OAuth returns can preserve the cookie;
- narrow Path appropriate to authentication flows where practical;
- explicit expiration;
- signed/integrity-protected by a server-only secret;
- one-time consumption after successful resolver handling.

The payload stores only normalized application-owned navigation state, conceptually:

```text
purpose
relativePath
safeCanonicalQuery (optional)
issuedAt
expiresAt
nonce
```

No scheme, host, credentials, access token, refresh token, password, recovery artifact, raw form payload, evidence identifier, or mutation body belongs in the intended-destination token.

## Route allowlist

Only supported **internal Owner destinations** may be restored.

Initial eligible route family:

```text
/dashboard
/dashboard/*
```

Additional authenticated Owner route families may be added only when their authorization and state semantics are defined.

The following are never accepted as intended Owner destinations merely because they are syntactically internal:

- `/signup`;
- `/login`;
- `/recovery`;
- auth/provider callback routes;
- `/ops/*` through the normal Owner authentication-return mechanism;
- arbitrary public/external redirects;
- protocol-relative paths such as `//example.com`;
- encoded values that normalize outside an allowed Owner route family.

O01 is reached by owner-state resolution, not by allowing a new account to force an onboarding bypass/return token.

## Query-state handling

Query state may be preserved only when it is already permitted by the locked canonical URL/query-state contract.

Rules:

- parse and normalize with route-specific schema;
- discard unknown/unsafe query parameters;
- never preserve secrets or transient sensitive state;
- never preserve arbitrary `url`, `redirect`, `callback`, or equivalent untrusted target parameters;
- canonicalize equivalent safe query state before signing/storing it.

Fragments are not authoritative return state.

## External input boundary

If an unauthenticated entry URL contains a `next`, `returnTo`, `redirect`, or equivalent parameter, it is **untrusted input**.

The server may convert it into an intended destination only after:

1. parsing it as a relative application path;
2. rejecting absolute/protocol-relative/external targets;
3. matching an allowed Owner route family;
4. normalizing safe route/query state;
5. issuing the protected intended-destination cookie.

The raw parameter is never blindly redirected to after authentication.

## Expiry and fallback

Baseline navigation-intent lifetime is **30 minutes**.

Expiry does not invalidate authentication or destroy persisted Working/Draft state. It only means the navigation hint is no longer trusted/restorable.

On expired, malformed, tampered, stale, deleted, or unauthorized destination state:

```text
owner-state resolver remains authoritative
→ active + complete falls back to D01
```

No error needs to reveal protected target existence.

## One-time consumption

After a valid intended destination is used following authentication/resolution:

- clear/expire the cookie;
- do not leave it available to unexpectedly redirect later logins;
- repeated callback/reload must not replay a consequential action.

A safe failed-auth attempt may leave an unexpired navigation token available for a later legitimate retry.

## Re-authentication action context

A sensitive re-auth flow may preserve where to return, but **must not encode the pending mutation itself into the intended-destination navigation token**.

For protected actions requiring re-authentication:

- navigation destination may use the normal protected return mechanism;
- pending action context is represented by a separate short-lived opaque server-side ticket/record when needed;
- the ticket binds at minimum to the expected Owner, action class, nonce, creation/expiry, and any target/revision identity required by that action;
- successful re-authentication satisfies identity freshness only;
- current actor, permission, target, state, and revision are revalidated;
- the mutation is never automatically replayed solely because re-authentication succeeded.

This preserves 11.3 Tier-1/Tier-2 semantics.

## Recovery boundary

A03 may preserve the same safe internal navigation intent through recovery when possible, but recovery links/codes/tokens are separate authentication artifacts and never become intended-destination payload.

Recovery success still runs the owner-state resolver first.

## Anti-enumeration / disclosure

Invalid or unauthorized intended destinations must not become existence or ownership oracles.

Where existence is protected, outward fallback may remain generic while internal telemetry retains the precise safe reason.

Do not emit full sensitive destination state to ordinary analytics/logs. Prefer coarse classes such as:

```text
restored
expired
invalid
unauthorized
fallback
```

## Security implementation requirements

Implementation must include tests for at least:

- valid internal `/dashboard/*` restoration;
- new/incomplete account cannot bypass O01;
- suspended account cannot bypass D10;
- external `https://evil.example` rejected;
- protocol-relative `//evil.example` rejected;
- encoded path traversal/normalization escape rejected;
- auth/callback/ops route rejected from Owner return token;
- unsafe query parameter stripped/rejected;
- tampered signature rejected;
- expired token rejected;
- consumed token not replayed;
- destination authorization rechecked after Login;
- re-auth success does not auto-execute the pending mutation.

## User Flow impact

No J1–J9 Mermaid topology change is required.

This decision concretizes the already locked J5/A01/A02/A03 rule that a returning Owner is restored to the intended authorized workspace after authentication when safe. It changes transport/security mechanics, not the user-visible journey sequence.

## Final lock

Spall Spill preserves protected Owner navigation intent through a short-lived, server-issued, signed, HttpOnly, one-time destination token containing only normalized internal navigation state. Account-state resolution and current authorization always override the token. Sensitive re-auth mutations use a separate opaque server-side action context and are never replayed from navigation state.
